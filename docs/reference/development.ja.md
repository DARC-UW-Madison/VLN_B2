# 開発と実験の手引き

[English](development.md) · [ホーム](../../README.ja.md)

> 文書種別：**参照資料**．

B2で再現可能な実験を行うまでの進め方を説明する．準備用ツールを実装し，
外付けホストの構成，実モデルの厳密なGPU読込，生成画像の1回の推論を確認した．その後，ZEDのRGB取得も一回成功した．継続観測，B2状態，機体の移動は未検証である．
現在利用できるコマンドは[現地での準備](../how-to/onsite.ja.md)を参照する．以下では，次の段階に進むために必要な証拠を説明する．

## 最初にローカルで確認する

リポジトリのルートでPython 3.10以降を使う．

```sh
PYTHONPATH=src python3 -m b2_tic_vla replay
PYTHONPATH=src python3 -m unittest discover -s tests -v
git diff --check
```

付属の再生データは3つの合成サンプルを評価する．最初の2件は候補指令が採用され，
最後は古い画像として拒否されてゼロの候補値になる．ニューラルモデルもハードウェアも使わず，移動指令を送信しない．
採用とは設定したソフトウェア上の検査に通ったという意味であり，経路に障害物がなくB2が安全に走れるという意味ではない．
設定例の上限値を実際に使う前には，別途承認と測定が必要である．
テストは合成データとメーカーの接続部のモックを使ってローカルの処理を検証し，実際のドライバーや学習済みモデルは検証しない．

### 準備段階で実行した確認

**2026-10-27**に，macOSのローカルホストとPython 3.14.7で，**85件の標準ライブラリのテスト**，
合成データのCLI再生，Ruff 0.17.3による設定済みのlint規則の検査が通った．本体・テストは
Python 3.10，単独の調査ツールは3.8向けに構文を確認する．構文解析は，その版での実行とは異なる．

`0dcf950`の公開前レビューでは，追跡対象の53ファイル，全14組の日英Markdown，到達可能な全Git履歴を対象に，
描画後のMarkdown，リンクと見出し参照，コマンド例と出典の日英対応，個人情報・秘密情報の検査，
ローカル記録・モデル成果物の除外を確認した．ローカルでwheelをビルドし，MITのライセンス文の同梱を確認した．
Dockerのビルド対象とコピー指定にもライセンス文と外部資料の説明を含めた．コンテナはビルドしていない．

実際の外付けJetsonにはSSHで接続し，Python 3.8.10で調査ツールを実行した．CUDAドライバ・デバイスの
照会と管理者権限でのDocker情報の取得も成功した．[確認済み構成](../records/target-baseline.ja.md)を参照する．
初回の検査ではコンテナのGPU演算，モデル読込，ZED撮影，B2動作までは検証していない．後の段階は下に区別する．
[実行環境の調査](../records/runtime-compatibility.ja.md)には未解決のチェックポイント読込制約を記した．
その後の[実行環境構築](../records/jetson-runtime.ja.md)では，JetsonにPython 3.11.18と専用venvを導入し，
対象機でも全85件のテストと合成データの再生が通った．Torchとは独立したネイティブCUDAの数値演算も成功した．
ソースと公開物の検査は，ハードウェアの動作や外部成果物の再配布許可を確認するものではない．

無人起動のネットワーク用ツールでは，認証ID・信頼設定の維持，秘密情報を出さない確認，
省略された既定値，パスワード不一致時に書き込まないこと，未対応プロファイルの拒否，
GDMの変更範囲に関する8件を追加し，ローカルとJetsonのvenvで**全93件**が通った．
対象機のシステムPython 3.8でNetworkManagerの読み取り確認も行った．操作者が入力する
Wi-Fi認証情報の保存，実際の再接続，電源投入からの復旧は，別の操作者向け確認として残る．
その後のMac用トンネルヘルパーでは，読み取り専用の状態確認，引数の検査，使用中ポートの保護，
専用masterを含め，動作と所有権に関する12件を追加した．ローカルの**全109件**が通った．
実際のバックグラウンドトンネルを起動し，別の呼び出しで確認した．HDMIなしのソフトウェア再起動後，
操作者がRDPの入力を確認した．物理的な電源の入れ直しや，非アクティブなeduroam設定の確認にはならない．
[システム全体像](system-overview.ja.md)を参照する．

さらに，保存済み設定の名前の厳密な一意選択，接続を有効にせず秘密も出力しない非アクティブな設定の保存，
パスワード入力前の拒否，設定別のバックアップの維持に関する4件を追加し，全109件になった．

tensor専用の接続部には，版を検査するチェックポイント読込，古いTorchでのsafetensors読込，
壊れた入力からpickleへ戻らないこと，基盤モデルのローカル・safetensors読込の強制に関する4件を追加し，
**ローカル・Jetsonで全113件が成功**した．実際の生成tensorによる試験は`tools/verify_tensor_loading.py`で，
モデル構築，GPU，外部の重みは使わない．モデル変換，全モデルの厳密な読込，記録済み画像の推論とは別の試験である．

CPU変換部には，固定した来歴，元のchecksum，通常のファイル，入出力の上限，上書きしないこと，
alias名の完全な維持，対応するCPU tensor，無関係な学習メタデータを省くことの8件を追加した．
**ローカル・Jetsonで全121件が成功**した．別のCPUコンテナで実際に生成したチェックポイントの変換と，
旧環境でのtensorの読戻しも成功した．[変換の手引き](checkpoint-conversion.ja.md)を参照する．その後，実モデルの厳密なGPU読込と生成画像の1回の推論が通ったが，実観測と非同期制御は未検証である．

## 1. システムを理解する

[構成と仕組み](architecture.ja.md)と[進捗](../status.ja.md)を読む．
チェックポイントとは保存されたモデルのパラメータである．推論はそのパラメータを使って予測を行う処理であり，学習ではない．
軌道は時刻に対応する位置を指定し，速度指令は現在どれだけの速さで動くかを指定する．
接続部では，確認済みの単位と座標系を使って両者をつなぐ必要がある．

図に描いた軌道がもっともらしいだけでは，ナビゲーションの成功とはいえない．
ロボットが軌道を実行し，新しい観測に反応し，意図した目的地に到達する必要がある．
以下の段階では，これらの問いを個別に確かめてから組み合わせる．

## 2. 実際の環境を特定する

モデルの依存パッケージを導入する前に，以下を環境仕様としてまとめ，レビューする．
接続先アドレスと認証情報は研究室の管理領域に置く．
詳しい確認項目，読み取り専用の調査コマンド，最初の回答用テンプレートは
[導入前に集める情報](deployment-intake.ja.md)を参照する．

| 項目 | 必要な情報 | 確認する理由 |
| --- | --- | --- |
| 機体 | B2の型式，ファームウェア，利用可能な高位API，停止と介入の挙動 | 制御の接続条件を決める |
| 計算機 | CPUアーキテクチャ，GPUとメモリ容量，OS，ドライバー，CUDAまたはJetPack | 互換性のある推論環境を選ぶ |
| カメラ | ドライバー，画像形式，解像度，周期，時刻，校正，取り付け位置の変換 | モデルの観測を機体に対応させる |
| 機体状態 | 取得可能な速度・位置・姿勢，座標系，周期，時刻 | 推論中の移動を復元する |
| 通信 | SDKの版，接続方法，時計の対応，実測した遅延 | 観測の不一致や古いデータの混入を防ぐ |

単独の環境調査ツールは，Python 3.8以降で動き，外部パッケージを必要としない．

```sh
python3 tools/inspect_target.py
```

導入済みのシステム情報を読み，不明，利用不可，未確認の項目を明示する．
パッケージの導入，リモートサービスへの接続，センサーの起動，GPUコンテナの動作確認は行わない．
ネットワークアドレスは明示的に指定した場合だけ出力に含める．
既定の出力にも研究室の情報が含まれる可能性があるため，共有前に内容を確認する．
外付けJetsonでは実行済みだが，未接続のB2を調査・検証するものではない．別のロボットの手引きからB2の構成を推定せず，ROS 2の必要性を確認してからディストリビューションを選ぶ．

**完了条件：** 非公開のチャットを読まなくてもハードウェアとソフトウェアを特定でき，
未確認事項ごとに次の確認方法が決まっていること．

## 3. オフラインでモデルの推論を再現する

実装済みの `infer` コマンドは，既存のローカルファイルを読み込み，記録済みの観測に対して
上流パッケージの同期予測APIを呼ぶ．意味情報のキャッシュの遅延をゼロとして扱い，論文の非同期実行は再現しない．
出力は現在の機体座標系における0.1秒間隔のXY位置であり，位置を累積加算しない．
チェックポイントの構造を調べ，パラメータを厳密に照合して読み込む．
実際に取得したチェックポイントとの互換性は，まだ実証していない．

再生時にはホスト時計の新しい時間区間を開始する．元の記録時刻は出典のメタデータとして保持するが，
再生した画像が現在の新しい観測であることを示すものではない．出力は計画であり，機体に送る指令ではない．
必要なローカルファイルと引数は[現地での準備](../how-to/onsite.ja.md)を参照する．

先に[外部資料の利用条件](../../THIRD_PARTY.ja.md)を確認する．上流のコミット，モデル配布元の版，
チェックポイントのチェックサム，依存パッケージの版，数値精度，入力の前処理を記録する．
外部資料は，公式の配布ツールを使い，このリポジトリとは別に取得する．

研究利用が認められた小さな記録を使う．画像の取得時刻と，対応する機体状態のサンプルを保持し，
座標系と単位を調べる．チェックポイントを読み込み，不足・余分なパラメータがないか調べ，
行動出力の形と意味を確認する．チェックポイントの不一致は設定の失敗であり，無視してよい警告ではない．

予測軌道を観測に重ねて確認する．初期化，定常状態の推論，観測の古さを別々に測り，GPUメモリ使用量を記録する．
画像欠落，機体状態の欠落，結果の遅延，不正な数値出力を試す．
プログラムは失敗を報告し，実行可能な指令を出さないこと．

**完了条件：** 指定した入力と版から，別の研究者が予測を再現できること．実機の移動インターフェースは接続しない．

## 4. 移動指令を送らずに実機の予測を確認する

`camera`，`state`，`record` コマンドで観測を取得できる．
`record` は画像1枚と受信した機体状態を保存し，受信時刻の差が0.2秒以内であることを確認する．
これはハードウェア同期ではない．メーカー由来の取得時刻は未検証のままであり，座標系も明示的に確認するまで不明のまま扱う．
推論に受け入れさせるためだけに，不明な速度の座標系を書き換えない．
連続したライブ予測，非同期キャッシュの一貫した更新，完全なリアルタイムの観測・制御ループは未実装である．

実際のカメラと機体状態の取得部を接続し，指令送信は無効のままにする．
承認された手動操作の手順で静止，直進，旋回の観測を集めて比較する．
画像と状態の時刻対応，カメラから機体への座標変換，キャッシュの時刻，予測の古さを確認する．

遅い推論や一時的なセンサー停止も含める．古い出力を現在のものとして示さず，期待する状態を報告するか確かめる．
確認用の出力には，取得時刻，予測時刻，座標系と単位，候補の指令，その指令を採用・拒否する理由を表示する．

**完了条件：** 変換と指令の拒否が正しいことを記録で示せること．この段階だけでは自律走行性能を確認したことにならない．

## 5. 指令経路を検証してからナビゲーションを評価する

現在のリポジトリにはモーターへの指令送信部がない．実装済みの `PathTracker` は，
指令を送らない評価のために前進と旋回の候補速度を計算し，横方向の速度はゼロにする．
データの妥当性，鮮度，設定した上限を調べるが，障害物との間隔は検証せず，
実時間で監視するwatchdogや非常停止も提供しない．B2の高位移動インターフェースとの接続は，別の後続段階である．

モデルによる指令を有効にする前に，実験区域，操作者の制御，速度・加速度の上限，停止距離，復旧手順を決める．
実際のファームウェアでSDKの戻り値と指令途絶時の挙動を確認する．
指令の失効と停止の処理はモデル推論から独立させる．SDKの呼び出し成功だけでは，機体が停止した証拠にならない．

管理された環境で接続部と軌道追従の試験を行い，合格後に短距離のナビゲーションに進む．
設定の調整と評価を分け，比較実験の前に課題，試行数，上限，成功条件を定義する．
手動介入，異常，衝突，不成功を含め，試みたすべての試行を記録する．

目的地への到達，介入，経路長，遅延の分布，停止動作，計算資源の使用量を測る．各指標の定義と分母を明記する．
条件をそろえて，仕様を明示した比較対象と比べる．別の機体や環境で発表された結果を代用しない．

**完了条件：** 方法，全試行の内訳，結果，失敗の分析，証拠から主張できる範囲を報告できること．

## 再現できる記録を残す

各実験について，以下を記録する．

- 問い，仮説，比較対象，事前に決めた判定基準．
- コードのコミット，モデル・チェックポイントの版とチェックサム，パッケージ・ファームウェアの版，
  ハードウェア，校正，設定，該当する場合の乱数シード．
- 入力データの版，指示文，手順，時刻，試行数．
- 測定結果，失敗，計画からの変更，分析方法，不確かさ．
- 承認された保管先にある証拠の場所とアクセス条件．公開する報告には，非公開の保管先アドレスや個人を特定できる録画を含めない．
- 結論，制限，結果を根拠に選ぶ次の実験．

生の録画，地図，モデルファイル，実行ログは研究室が認める保管先に置く．
コミットするのは，公開可能な内容に整理した報告，設定例，小さな合成データなど，共有を認められたものだけとする．
無視パターンは作業を助ける仕組みであり，新しいファイルを公開してよいという保証ではない．

## 確認に失敗したとき

| 観測された問題 | 次に調べること |
| --- | --- |
| チェックポイントのキーやテンソルの形が合わない | コードの版，モデル設定，チェックポイントを照合し，接続作業を止める |
| 直進するはずの軌道が曲がる，または左右反転する | 軸，旋回角の符号，カメラの座標変換，増分の合成方法を調べる |
| 予測が遅れて見える，または不連続になる | 取得時刻，時計の対応，キャッシュの交換，キュー内のデータの古さを追う |
| SDKは指令を受け付けるが機体の動きが違う | 承認された手順で，ファームウェア，制御モード，単位，指令の制御権を確認する |
| 結果を再現できない | 調整を始める前に，版，入力，校正，乱数シード，試行の定義を比較する |

原因と修正の確認結果を該当する手引きに記す．次の段階に進めるようになったら，
両言語の文書と[進捗](../status.ja.md)を更新する．
