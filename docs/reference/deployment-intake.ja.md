# 導入前に集める情報

[English](deployment-intake.md) · [ホーム](../../README.ja.md)

> 文書種別：**参照資料**．

環境仕様を作るための確認項目をまとめる．不明な項目は不明と答えてよい．推測で埋めず，何を調べれば分かるかを記す．
最初は前半の表から始め，後半の測定は接続作業の際に一緒に進める．
この手引きに記す確認コマンドや移動指令は，対象のB2では実行していない．
B2，Jetson AGX Orin，ZED 2i，Livox Mid-360は特定済みで，Dockerと研究室GitHubの利用許可がある．
情報を集める前に[対象の構成](../status.ja.md)を読み，確定済みの事項は再度尋ねない．
ソフトウェアの詳細は，接続できるようになってから調べられる．

## 情報を具体的に確認する理由

以前のUnitree接続の記録には，ネットワークインターフェースの選択，ブリッジの転送，
トピックの選択，SDKのローカル変更という別々の問題があった．今回の確認では，記録と現存するスクリプトの不一致も見つかった．
過去の対処法は，B2で確かめる仮説として扱い，そのまま設定手順にしない．

今回は次の到達状況を別々に確認する．

- 正しい機体への通信が成立する．
- 有効な機体状態が届き，更新される．
- 現在のカメラ画像を取得できる．
- 使用する移動・停止インターフェースと，その動作を確認できる．

SDKのimport成功，pingの成功，トピックの発見，画面上のゼロ表示だけでは，これらすべてを確認したことにならない．
スクリプトが存在するだけでも，実行に成功した証拠にはならない．

## 実装方針を決める前に必要な情報

| 調べる項目 | 分かるとよい内容 | 決められること |
| --- | --- | --- |
| 機体と開発権限 | B2と確認済み．ファームウェアとアプリの版，メーカーの開発資料を読めるか，高位制御を使えるか | 正しいAPIと対応する操作 |
| 現在動いている手順 | どのPCでどのスクリプトを動かすか，SDKのコミットと独自変更，状態・画像・移動・停止のうち実際に成功したもの | 実績のある出発点 |
| 各PCの構成 | CPUアーキテクチャ，GPUとメモリ容量，システムRAM，空きディスク，OS，Python環境，ドライバー，CUDAまたはJetPack，既存のPyTorch | 推論の実行場所と互換性のあるパッケージ |
| 物理的な接続構成 | 作業PC，機載PC，運動制御用PC，カメラを何で接続するか，有線・無線，ルーティング，ブリッジ，VPN，コンテナの有無 | 各処理の配置 |
| 画像の取得 | カメラの型式と取り付け位置，内蔵か追加か，ドライバーまたはAPI，現在画像を復号・表示できるか，対応する解像度と周期 | 観測取得部と前処理 |
| 機体状態の取得 | 位置・姿勢・速度・旋回角速度が実際に届くトピックまたはAPI，型と観測した更新周期 | 状態取得部と遅延中の移動の補償 |
| 指令の制御権と停止 | 既存の自律走行・遠隔操作などの送信元，操作者の優先権，仕様上の指令有効期限と更新周期，独立した停止と復帰の方法 | 制御権の管理と異常時の処理 |
| 最初の研究課題 | 指示文の例，屋内・屋外，距離，通路の余裕，静止・移動障害物，最初の成功条件 | 最小の実験と評価範囲 |
| 作業の条件 | B2とPCを使える日時，研究室の既存手順と録画，パッケージ導入・コンテナ利用の可否，遠隔で調査できるか | 直ちに着手できる作業 |

パスワード，秘密鍵，シリアル番号，研究室の正確な場所は送らなくてよい．最初は機器の役割だけを示した接続図で十分である．
実際のアドレス，認証情報，SSID，非公開のネットワーク設定は，承認されたローカルの保管先に置く．
独自コードと文書には[MITライセンス](../../LICENSE)を適用する．公開の研究室リポジトリは
[VLN_B2](https://github.com/DARC-UW-Madison/VLN_B2)で，push権限を確認した．
第三者のソフトウェア，重み，データにはそれぞれの利用条件が適用される．

## 接続作業で詳しく確かめること

### 1. SDKと実行環境の特定

SDKの正確なコミットと，上流からの変更の有無を記録する．起動コマンドが使うPythonと，実際に読み込むモジュールの場所を特定する．
編集可能なインストールでは，想定と異なるコピーを参照していることがある．
CycloneDDSのPythonパッケージとネイティブライブラリの版，`CYCLONEDDS_URI`，インターフェースの選択，
ROSを使う場合のROS・RMW設定を記録する．コンテナを使う場合は，内部の設定とホストの設定を区別する．

[SDKの通信初期化部](https://github.com/unitreerobotics/unitree_sdk2_python/blob/master/unitree_sdk2py/core/channel.py)はDDSの設定を構成する．
ローカルで修正された実装では，設定の選択方法が異なる可能性がある．
環境変数がプログラムのインターフェース指定に常に優先すると断定する前に，実際のコードを確認する．
最初の診断として過去のパッチを適用したり，設定を全体で解除したりしない．

[TIC-VLAの学習用依存定義](https://github.com/ucla-mobility/TIC-VLA/blob/main/requirements-train.txt)は，
CUDAを指定したPyTorchビルドを固定している．これはJetsonで検証済みの導入手順ではない．
対象プラットフォームを特定してから推論用の依存関係を選ぶ．
最初のオフライン推論にIsaac Simや学習用の依存関係が必要と決まったわけではない．

### 2. 通信の挙動

対象の機体とDDSドメインを特定する．各PCに届くインターフェース，マルチキャストか明示的なpeer指定か，
アクセスポイントの端末間分離やファイアウォールによる制限の有無を記録する．
ROSを使う場合は，RMW，メッセージ定義，QoS，ドメインの対応を確認する．
`ROS_DOMAIN_ID` を変更するだけでは，機体や別途初期化するSDKの設定は変わらない．

ブリッジやコンテナがある場合，変更を提案する前に転送設定とパケットのカウンターを調べる．
承認されたネットワーク変更については，再起動後の持続性と，接続を失った場合の復旧経路を記録する．
広範囲のファイアウォール許可をコピーしたり，ファイアウォールを無効にしたり，ブリッジを必須と仮定したりしない．

使用する回線で状態と画像を同時に受信して測る．pingの平均値だけでは，画像の古さ，欠落，
遅延のばらつき，一時的な混雑は分からない．同じドメインに複数の機体や既存の制御プログラムがいないかも調べる．

### 3. 機体状態の意味

必要な各項目について，トピック・API，メッセージ型，発行元のサービス，発行元の時刻，受信時刻，
座標系，単位，想定する周期を記録する．承認された手動操作で値が変わり，欠落が正しいゼロ値に見えないことを確認する．
位置推定の原点，リセット，ドリフト，追加の自己位置推定なしで位置を取得できるかを特定する．

鉛直速度と旋回角速度を混同しない．四元数の成分順と，位置・並進速度・姿勢それぞれの座標系を明記する．
ROSのオドメトリでは，実際の発行元，`header.stamp`，`frame_id`，`child_frame_id`，TFの担当，QoSを確認する．
`/odom` を購読するだけのプログラムは，SDKからROSへの変換部を作るものでも，これらの意味を検証するものでもない．

### 4. カメラと時刻の対応

Go2用の映像クライアントが動くと仮定せず，B2で対応する取得方法を確認する．
RGBとBGRの順序，圧縮，画像の回転，校正，画角，取り付け高さ・角度，カメラと機体の間の座標変換を記録する．
カメラが複数ある場合，ナビゲーションに使う映像を特定する．

撮影時刻を取得するか，取得できないことを明示する．ファイル名の時刻や画像要求の完了時刻は，撮影時刻とは限らない．
継続的に受信できるFPS，画像の古さ，欠落を測り，可能ならキュー，圧縮，転送の遅延を分ける．
時計の基準と，画像を機体状態に対応させる方法を特定する．
正確な校正と遅延の測定は，最初の機器構成の確認後でよい．

### 5. 指令と停止の動作

有効な制御モード，APIの版，対応する移動方向，単位，上限，必要な指令周期，戻り値，競合する送信元を確認する．
指令の送信と，実際の動作を確認したことを区別する．
[B2専用の公式例](https://github.com/unitreerobotics/unitree_sdk2_python/blob/master/example/b2/high_level/b2_sport_client.py)は，
APIの参考資料として扱い，実行を承認済みの試験プログラムとして扱わない．

指令途絶，送信プロセス終了，処理停止，操作者の介入，非常停止，再開について，メーカーと研究室の手順を入手する．
送信側のタイムアウトから停止を送れるのは，そのプロセスと通信経路が動く間だけである．
切断後の機体の動作までは保証できない．受信側の指令失効と独立した停止経路は，承認された試験手順で確認する．
この確認表を埋めるためだけに，移動中の機体を意図的に切断しない．
別機種のリモコン操作を流用したり，`Damp()` を独立して検証した非常停止と同一視したりしない．

### 6. 機器搭載と実験の制約

計算機やカメラを追加する場合は，許容積載量，取り付け箇所，電源の電圧・電流・コネクター，
冷却，配線の制約を機体資料と研究室で確認する．これは必要になった場合の確認事項であり，
既存構成を調べる前に機器を購入するという提案ではない．

最初の課題でRGBと機体状態だけを使うか，LiDARによる自己位置推定や別の障害物監視も評価するかを明確にする．
モデルのRGB入力を接続するために，LiDARの接続一式が必ず必要になるわけではない．
研究上の比較では，性能を主張する前に，比較対象，試行の定義，到達判定の許容範囲，介入の扱い，
利用できる正解データを決める．人物や研究室内を記録するデータの録画・保管・共有条件も確認する．

## 最初の情報を調べる方法

対象のLinux計算機では，次のコマンドは環境の読み取りだけを行う．

```sh
uname -m
uname -r
cat /etc/os-release
python3 --version
df -h .
free -h
```

対応するNVIDIAホストで利用可能なら `nvidia-smi` を使う．Jetsonでは，
ファイルとパッケージ用ツールが存在する場合に `/etc/nv_tegra_release` と
`dpkg-query -W nvidia-jetpack nvidia-l4t-core` を調べる．
パッケージがないことも記録する結果であり，その場で導入・更新する理由にはしない．

アプリケーションに使う予定のPython環境では，次を調べる．

```sh
python3 -m pip show torch torchvision transformers cyclonedds unitree_sdk2py
```

SDKのソースがある場所で `git rev-parse HEAD`，`git status --short`，`git diff HEAD` を実行すると，
ソースの版と，追跡済みファイルのステージ済み・未ステージの変更を確認できる．statusに出る未追跡ファイルのうち，関係するものは個別に調べる．
出力は共有前に手元で確認する．パッケージの場所や差分には非公開の情報が含まれる場合がある．
これらのコマンドを，モデルの読み込みやロボットの接続に成功した証拠として扱わない．
