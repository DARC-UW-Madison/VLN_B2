# 配置方針：計算機，コンテナ，ROS，センサー

[English](deployment-design.md) · [文書目次](README.ja.md) · [用語](glossary.ja.md)

準備している環境の役割分担と，採用した方法の理由を説明する．設計と実測を区別する．
外付けJetsonのZED画像によるモデル実行，内蔵i7の状態・映像受信，既にダンピング中の一回の要求まで成功した．
外付けからの直接DDS通信とモデルによる制御は未完成である．現在のhardware・softwareは，先に
[実測した計算機と通信の順序](network-topology.ja.md)を読み，このページでは配置の選択肢を確認する．

## 1．どこで計算するか

プログラムは，そのプロセスが動く計算機のCPU・GPUで命令を実行する．Macでファイルを
編集しても，Macがそのプログラムを実行するとは限らない．SSH接続したMacの端末は，
Jetson上のシェルへキー入力を送る．そのシェルでPythonを起動すると，JetsonのCPU，
メモリ，ディスク，利用可能なGPUを使い，Macには端末の出力が返る．リモートデスクトップも
画面と入力を転送する方式であり，モデルのGPU計算をMacへ移すものではない．

| 計算機など | 想定する担当 | 完成後のローカル実行中に必要か |
|---|---|---|
| Mac | コード・文書の編集とレビュー，遠隔作業の開始，選んだ結果の表示 | 必須ではない．任意の監視は実験の監督方針に従う |
| 外付けAGX Orin | 観測の取得，TIC-VLA，軌道追従，将来の唯一の指令送信部の監督，ログ保存 | 必要 |
| 内蔵Intel i7開発用PC | 既存の内部状態・映像へのアクセス．アプリケーション中継の候補 | 実測したSSH・i7経路では必要．追加の内蔵Jetsonは未確認 |
| 既存の動作制御系 | B2の対応インターフェースの先で，歩行・バランス・アクチュエーターを制御 | 必要．物理ホストと内部実装は未確認 |
| GitHub | レビュー可能なソース履歴と共同開発 | 準備済みのローカル実行ではインターネット依存にしない |
| Hugging Faceなど承認済みの配布元 | 実験前に，承認したモデル資材を取得 | オフライン実行の準備が済めば不要 |

外付けJetsonはナビゲーション用であり，B2のバランス制御を置き換えるものではない．
経路の予測，その経路を速度指令として追う処理，脚の関節制御はそれぞれ別の計算である．
将来の上位速度指令はB2の既存の制御系を通す．そのサービスの実ホスト，制御権，
運転モード，停止動作は現地で調べる必要がある．

## 2．Macに全ファイルやDockerが必要か

必要ではない．負担を抑える基本形は，Macには編集・レビュー用の小さなソースを置き，
実行環境はJetsonへ置く構成である．SSH対応エディターでJetsonのファイルを直接編集し，
Macには必要な文書・結果だけを置く方法もある．Macのコピーはオフライン編集や復旧に便利だが，
TIC-VLAの必須条件ではない．変更は明示的なコミットとして保存し，未完了の研究成果が
遠隔作業用ディレクトリの一か所にしか存在しない状態を避ける．

| 資材 | Mac | 外付けJetson | 公開ソースリポジトリ |
|---|---|---|---|
| 独自Python，テスト，Dockerfile，文書 | 便利だが，遠隔編集なら必須ではない | ツールの実行時に必要．承認したアプリ用イメージへ含める場合もある | レビュー後に含める |
| 利用制限のある本家TIC-VLA実装 | 通常の編集には不要 | 別に承認し，版を固定した実行入力 | 含めない |
| モデルの重み，tokenizer・設定資材 | 不要 | オフライン推論前に承認済みのものをローカルへ用意 | 含めない |
| Linux ARM64 CUDAイメージとビルドキャッシュ | 不要 | SSDに準備したイメージ・レイヤ | レシピと公開可能なメタデータだけ |
| 個人の認証情報，SSH・Tailscale状態 | 各計算機自身のアクセス情報だけ | プロジェクト・イメージの外でホストが管理 | 含めない |
| 生のカメラ画像・動画，実験ログ | 許可された結果を選んで置く | 承認された研究用ストレージ | 自動公開しない |

MacのDockerは，具体的な開発用途があるときの任意の道具である．JetsonのイメージはLinux
ARM64とNVIDIAのJetson用ドライバを使う．Apple SiliconとARM64というCPU命令系統が
共通でも，MacがJetsonのGPU・ドライバを持つわけではない．エミュレーションで
イメージを動かしても，OrinのCUDA検証にはならない．標準ライブラリ中心の軽いテストや
文書作業には，MacのDockerも重みも不要である．

Gitは各計算機のバージョン管理で，GitHubはその共有先である．ロボットを実行したり，
フォルダを常時同期したりする仕組みではない．ユーザーからGitHub運用開始の連絡を受けたら，
レビューしたソースを公開し，Jetsonではcloneか，識別できるソースリリースを使う．
`git pull`が更新するのはソースであり，依存の導入，モデルのコピー，個別設定の移行，
イメージの再ビルド，アプリの再起動は行わない．各実験ではソースの版，イメージID，
モデル資材の版，実験設定を別々に記録する．

現在Jetsonにあるのは転送したソースアーカイブで，Gitのcloneではない．そこで
`git pull`を実行したり，cloneのようにするためにGit対象外の`.venv`・`local/`を
上書きしたりしない．配布方式を変える際は既存のローカル状態を保全する．
ソースはまだpushしておらず，本文によって配布方式を変更したわけでもない．

## 3．直接実行できるのに，なぜDockerを使うか

Dockerは任意の梱包方法であり，モデルの数学的な必須条件ではない．互換性のある環境を
ホストへ直接作っても，同じ計算はできる．今回は別のPython・PyTorch構成を試す際に，
既存のUbuntu 20.04，システムPython 3.8，ROS Foxy，ZED，他のユーザーの作業を
維持するため，推論用の環境を分けた．依存環境をできるだけ分離したいという要望にも対応する．

| 方法 | 分離するもの | 負担・限界 |
|---|---|---|
| ホスト上のPythonとvenv | プロジェクトのPythonパッケージ | ネイティブライブラリ・SDKはホストとの互換性が必要．ファイル・通信のサンドボックスではない |
| Jetson上のDocker | アプリのファイルシステム，Python，ユーザー空間の多くのライブラリ | イメージ・ビルド・保存容量の管理と，デバイス・マウント・通信の明示設定が必要．ホストのカーネル・ドライバを共有 |
| GPU対応の仮想マシン | 仮想化とデバイス割当てに対応した別OS | 今回の方式ではなく，Dockerが提供するものでもない |

起動，通信，デバイスドライバ，Dockerデーモンはホストが担当する．イメージは保存した
ファイルシステムのひな型で，コンテナはそこから作ったプロセスの実行環境である．
NVIDIAのコンテナランタイムが，対応するGPU機能をそのプロセスへ公開する．計算は実際の
Jetson上で行い，Dockerの中に別の物理計算機があるわけではない．ビルドでライブラリが
入る先はイメージのレイヤであり，ホストのvenvではない．停止すると実行中のプロセスの
メモリは解放されるが，明示的に削除しない限りイメージ，マウント先のログ，重みは残る．

準備済みの`vln-b2-runtime:jp5`にはPython 3.11.18，ローカルでビルドしたTorch 2.2.2・
torchvision 0.17.2，依存先，モデル不要の検査スクリプトがある．既定の起動処理は検査であり，
ナビゲーションアプリではない．重みと，完全なライブB2アプリは入っていない．このレシピには
ROSディストリビューションやZED SDKも追加していない．ホストのSDKが自動的にコンテナ内へ
現れることもない．古いTorch候補にはチェックポイント読込の未解決事項があり，
演算・import検査の合格だけではモデルを読み込めない．[互換性](runtime-compatibility.ja.md)を参照する．

具体的なドライバ対応や保守上の都合が環境分離の利点を上回るなら，ホスト直接実行も候補になる．
その場合もPython・ネイティブライブラリ・ドライバの構成を明示する．Dockerを外すだけでは
CUDA ABI，チェックポイントの安全な読込，センサーの権限，本家の利用条件は解決しない．

## 4．ROSはDockerの中で動かすか

ROS 2はロボット用プログラムを作るフレームワーク・ライブラリ群である．ノードはROSのAPIを
使うプロセスで，トピックは型のあるpublish・subscribeの接点である．ホスト，一つのコンテナ，
複数のコンテナ，内蔵計算機のいずれにも配置できる．配置の正解をDockerが決めるわけではなく，
ロボット全体を一つのROS環境へまとめる必要もない．

最初の外付けB2状態取得では，独自コードからUnitree SDK2を直接呼べる．

```text
External application -> Unitree SDK2 -> CycloneDDS / RTPS -> IP / Ethernet
                    -> reachable B2 service -> existing locomotion system
```

SDK→ROS→機体という順序は必須ではない．選んだセンサー，自己位置推定，記録，表示が
適したROSインターフェースを持つ場合にROS 2が役立つ．既存サービスは維持する．
[Unitree公式のROS 2連携](https://github.com/unitreerobotics/unitree_ros2)はDDSの相互接続を説明するが，
型，発見設定，ドメイン，QoS，到達可能なインターフェースが対応する必要がある．
任意のROSトピック名やドメインを一致させるだけでは互換性は成立しない．

ホストにFoxyがあるだけで，全プロセスがROSノードになるわけではない．現在のCLIはPythonの
アダプターを使い，推論イメージへROSを追加していない．新しいROSの版の選定，
ライブのROS接続の構築，内蔵サービスのコンテナ移行もまだ行っていない．

## 5．別のコンテナ同士で通信できるか

できる．ただし，アプリのメッセージを交換できることと，Python変数，ファイル変更，
デバイス，別計算機の時計を自動共有することは異なる．送受信者の間で，フィールド，
座標系，発生・受信時刻，単位，画像形式，スキーマ版，鮮度，入力が止まった場合の動作を決める．

| 方法 | 運ぶもの | 注意する境界 |
|---|---|---|
| ユーザー定義のDocker bridge | 同一ホストのコンテナ名で指定するTCP・UDPサービス | `localhost`は自分のコンテナであり，別コンテナやホストではない |
| Linuxのhost networking | ホストのインターフェース・ポートを直接利用 | 物理DDS経路を単純化できるが，通信の分離がなくなる．機体向け通信の出口を指定する |
| 明示的にマウントしたUnix domain socket | ローカルプロセス間の構造化メッセージ | 権限，直列化，上限，所有者の定義が必要 |
| 共有メモリの画像バッファ | 画像全体のコピー回数を減らした大量データ | プロトコル，同期，サイズ・寿命管理，鮮度検査が必要 |
| 読取専用の入力・出力マウント | 記録済みデータのオフライン処理用ファイル | フォルダを共有するだけでは，堅牢な実時間メッセージ通信にならない |

方式の候補を示したもので，全てを実装したわけではない．Docker公式の
[bridge](https://docs.docker.com/engine/network/drivers/bridge/)と
[host network](https://docs.docker.com/engine/network/drivers/host/)に通信方式の違いがある．
ポート公開は指定したポートの対応付けであり，DDSの発見・multicast・動的な宛先を
一括解決するものではない．Docker bridgeを使うために大学Wi-FiとB2をbridgeする必要もない．

まずドライバとSDK受信を個別のプロセスとして確認し，次に一つの推論プロセスへ記録済み入力を渡す．
ライブの境界は必要になってから追加する．ホストで画像・状態を取り，限定したIPCで推論コンテナへ
渡す案と，通信を明示設定した機体側コンテナの案がある．どちらも未実装で，最終選定していない．
Dockerが複数のサービスを動かせるという理由だけで，構成を分割しない．

## 6．どのカメラを使い，内蔵PCは何をするか

最初の試験候補は，外付けZED 2iを外付けJetsonへUSBで直接つなぐ経路である．
画像取得を一つのケーブル，一つのホスト，一つのSDKに絞れる．機体へ取り付ける前に机上で試せ，
未確認の内蔵画像配信を最初に解決する必要もない．段階的に導入するための選択であり，
B2のカメラが不適切，あるいは将来も使わないと結論したわけではない．

```text
Candidate A: external ZED -> USB -> external host ZED SDK -> RGB observation
Candidate B: built-in camera -> attached onboard host/driver -> defined network
             stream -> Ethernet -> external receiver -> RGB observation
Mid-360: power + Ethernet -> its actual receiving host/driver -> possible
         point cloud/localization/obstacle pipeline, not currently implemented
```

Ethernetで運べるのは，接続先が配信するデータである．内蔵USB機器がローカルUSBとして
見えるようになるわけではない．候補Bでは，カメラ・ドライバ，ROSトピックなどの配信方式，
権限，画像符号化，周期，バッファ，座標系，時刻の意味を特定する．既存の利用者が
カメラを占有していないか確認し，その動作を妨げない．

現在のZEDアダプターは，補正した左カラー画像を要求し，深度は**無効**にしている．
RGB-D機能やLiDARがあることと，モデルが深度・点群を使うことは別である．最初のTIC-VLA入力は
RGB，指示，モデルが期待する状態特徴である．深度・LiDARを自己位置推定や障害物検査へ使うには，
別に検証した処理系が必要になる．予測経路と速度の制限だけでは障害物回避にならない．

到達できた内蔵PCはIntel i7で，TIC-VLAを動かさずに既存の状態・映像へアクセスできた．
追加の内蔵計算機と，自己位置推定を担当する機器は未確認である．内蔵画像が適切なら，
視野・取付け・時刻の整合性を評価して外付け画像を置換・補完できる．カメラの変更は
学習済みの視覚入力やカメラ・機体間の幾何を変えるため，JPEGが見えただけでモデルに
適しているとは判断しない．内蔵の動作制御系も，引き続き既存の歩行を担当する．

## 7．将来の実行全体を順番に追う

1. Jetsonで承認済みのコード・資材・設定，保存先，センサー，B2状態取得を確認する．
   GitHub・クラウドへのアクセスを必須にしない．
2. 明示した監督プロセスの下で，観測・未armed状態のローカルアプリを起動する．
   健全性を報告し，ローカル停止を受け付け，再起動だけで移動可能状態へ戻さない．
3. カメラが元・座標系・時刻を識別した画像を取得する．状態受信が既知の規約で姿勢・速度を取る．
4. ローカルモデルが画像・指示・状態から経路を予測する．予定する非同期キャッシュには
   参照姿勢・時刻を保持し，古い経路を現在の機体座標系の新しい経路として扱わない．
5. 明示的なarmed操作の後，唯一の追従・制御権管理部が上限と鮮度を確認した速度指令を作る．
   B2の制御系が歩行・バランスを実行する．
6. ローカルの期限・watchdogと，独立して確認した既存リモコン手順が，古い入力，
   プロセス・通信障害，操作者の介入へ対応する．
7. 停止・disarmし，結果をローカルへ保存する．レビューした要約だけをMac・承認した共有先へ出す．
   成功した試行も失敗した試行も記録する．

ライブサービス，キャッシュ，armed操作，指令送信は将来の作業である．現在の観測ツールと
オフライン推論は，このループを実装していない．次の検証段階は
[オフライン運用](offline-operation.ja.md)，[実行の流れ](runtime-flow.ja.md)，
[現地手順](field-network.ja.md)を参照する．
