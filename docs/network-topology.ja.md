# コンピューター，ネットワーク，SDK，ROS 2の役割

[English](network-topology.md) · [ホーム](../README.ja.md) · [現地手順](onsite.ja.md)

最初に確かめるのは，各サービスがどこで動き，外付けJetsonからどう到達するかである．
ROS 2の追加，コンテナ，ネットワークブリッジ，モデル推論の導入より先に確認する．
**外付けJetsonは機体とは別に置かれている**．画面・キーボードを直接使え，MacからTailscale経由の
SSHも独立に確認できた．有線ポートはキャリアもアドレスもなく，B2への接続はまだ確認していない．
[確認済み構成](target-baseline.ja.md)を参照する．別の内蔵Jetsonがあり，さらに動作制御用の
コンピューターがあると報告されているが，正確な実体，サービスの配置，配線は未確認である．

## 外付けJetsonから何を制御できるか

外部コンピューターを，B2の公開されている高位歩行APIのクライアントにできる．
公式の[B2 SportClient](https://github.com/unitreerobotics/unitree_sdk2_python/blob/master/unitree_sdk2py/b2/sport/sport_client.py)
には速度要求と停止要求がある．このため，外側で認識・計画し，既存の機体側で歩行する役割分担を
検討できる．ただし，今回の機体でのサービスの動作先，到達経路，動作モード，制御権，実際の
停止挙動は別途確認が必要である．`Move`は応答を待たない呼び出しなので，返り値だけで
実際の動作を確認したことにはならない．

目標は，外付けJetsonでTIC-VLAを開発・実行し，既存の歩行ソフトウェアを維持することである．
必要な状態取得・制御サービスとセンサー映像へアクセスできれば，内蔵ソフトウェアを変更せずに
済む可能性がある．一方，既存の自己位置推定，センサードライバ，ネットワークの隔離，制御の
優先順位によっては，内蔵Jetsonの調査やサービスとの接続が必要になる．高位歩行APIへ接続
できることは，ロボットの全機能へ無制限にアクセスできることではない．

Unitreeの[B2仕様](https://www.unitree.com/b2/)は，プラットフォーム用とユーザー開発用の
計算機を区別し，複数の構成を示している．これだけでは研究室の機体構成は確定しない．
「3台＋Mac」は調査の出発点として扱い，内部構成を網羅した確定図とは扱わない．

| 役割 | 想定する担当 | 確認する証拠 |
|---|---|---|
| Mac | 編集，コード転送，必要なら外付けJetsonへのSSH，結果の確認 | 実際の管理用接続．DDSへの参加は必須ではない |
| 外付けJetson | カメラ入力，TIC-VLA推論，追従計算，将来の単一の指令送信元 | OS／L4T，メモリ，インターフェース，SDKサービスへの到達，GPU環境 |
| 内蔵Jetson | 既存サービスの維持．センサーや自己位置推定を提供している可能性 | モジュールの実体，稼働サービス，インターフェース，センサーの接続先 |
| 動作制御系 | 既存の歩行，姿勢安定，アクチュエーターの制御を維持 | メーカー・研究室の接続仕様，サービスの終端，運用手順 |

1台に複数のIP，別名，コンテナ，仮想インターフェースがある場合もある．近隣キャッシュや
見覚えのあるIPだけでコンピューターを識別しない．SDKのサービスが動くホストと，最終的に
アクチュエーターを動かす制御器が同一とも限らない．

## 目指す接続と，まだ確認できていない配線

```text
Mac -- management link / optional SSH --> External Jetson
                                           |
                                 robot-facing Ethernet
                                           |
                              B2-side network (unverified)
                                  /                 \
                       Onboard Jetson       Published walking service
                       sensors/services       -> motion-control system
```

これは論理的な配置案である．スイッチの構成，VLAN，ルーター，サービスの実行先，到達性は
未確認であり，外部Ethernetポートから内部の2台が両方とも直接見えると断定する図ではない．
ケーブルの両端は実物で確認する．ZEDのUSBとMid-360のEthernetも，どのホストへ接続して
いるかを記録する．機種名だけでは，データの行き先はわからない．

機体向け通信は，外付けJetsonの有線接続を優先する．Wi-Fiや別のインターフェースで，Macの
管理用通信とインターネット接続を独立して扱える．構成を決める前に，サブネットの重複や
競合する経路がないかを確認する．プログラムをJetson上で動かす場合，
MacのSSH接続とJetsonのDDS通信は別の接続である．この設計ではMacのパケットを機体LANへ
転送する必要がなく，Wi-Fi／Ethernetのブリッジも不要である．既に動作するブリッジがある場合は，
役割と復旧経路を調べるまで維持し，この配置案だけを根拠に削除しない．SSHのトンネルだけで
一般的なDDSネットワークを置き換えられるわけでもない．

## 通信を階層に分けて考える

1. **Ethernet／IP：** 配線，リンク状態，アドレスとプレフィックス，経路，使用する
   インターフェースを扱う．似たIPが付いているだけでは通信経路ができたとはいえない．
2. **DDS：** 通信相手の発見とデータ交換を扱う．インターフェース，ドメイン，発見の設定，
   メッセージ型，QoS，ファイアウォールの挙動を合わせる必要がある．
3. **Unitree SDK2：** DDS上で状態取得や機体への要求を扱うAPIである．外付けJetsonへの
   ROS 2の導入は必須ではない．
4. **ROS 2：** ノード，トピック，センサー処理，SLAM，記録，可視化などに使う任意の
   枠組みである．対象とDDS／RMWや通信条件を合わせる必要があり，導入するだけでB2との
   ネットワークが設定されるわけではない．

Unitreeは[SDK2とROS 2のDDSでの相互接続](https://github.com/unitreerobotics/unitree_ros2)を
説明している．ROS 2から互換メッセージで通信でき，必ずしもSDKを包む必要はない．
ROSの接続部は，アプリケーションのインターフェースや座標系を実際に変換するときに役立つ．
外付けSDKクライアントとB2の間に，自動的に必要になるものではない．最初の外部確認に
SDK2を使うという理由で，既存の内蔵ROS 2サービスを停止しない．状態の読み取りは複数でも
よいが，複数の独立した指令送信元には制御権と優先順位の設計が必要になる．

Pythonの[通信初期化部](https://github.com/unitreerobotics/unitree_sdk2_python/blob/master/unitree_sdk2py/core/channel.py)
はドメインIDとインターフェースを引数に取り，プロセス全体で共通のDDS初期化を行う．
`ROS_DOMAIN_ID`はROSプロセスの設定であり，変更しても別のSDKプロセスへ渡した引数は
書き換わらない．本プロジェクトの確認コマンドは既定値0で，`--domain-id`でも指定できるが，
**0は今回のB2で測定した値ではない**．研究室で動作する設定やメーカー資料から，接続する
サービスのドメインを特定する．値を順に変えたり，販売店の設定をそのまま流用したりしない．

`CYCLONEDDS_URI`とプログラムからの設定がどう組み合わさるかは，導入されたSDKの初期化処理と
独自変更を見て判断する．環境変数が必ず優先されるとは仮定しない．最初は新しい端末を使い，
関係する環境設定を記録してから，必要性が確認できた変更だけをプロセス単位で行う．

## 単体での環境構築，アカウント，遠隔操作

具体的な操作は[ホストの初期設定手順](jetson-bootstrap.ja.md)を使う．
遠隔経路にはTailscale SSHを選び，Tailscale経由の管理接続を独立に確認した．完了した確認は
確認済み構成を参照する．

外付けJetsonは，B2へ取り付ける前に机上で準備できる．目指すアプリケーションの流れは，
画像・指示 → TIC-VLAの経路予測 → 追従計算 → Unitree SDKの速度要求 → 既存のB2歩行制御
である．これは配置の目標であり，指令送信部と非同期ライブ推論の結合は未実装である．

| 要素 | 担当 | 最初の方針 |
|---|---|---|
| JetPack／CUDAと互換性のあるPyTorch | ホストのGPU対応とモデル実行 | 導入済みL4Tと実行環境を調べてからパッケージを選ぶ |
| Unitree SDK2 | DDSによるB2の状態取得と機体への要求 | 最初の状態受信はホスト上で確認する．ROS 2は必須ではない |
| ZED SDK | ZEDカメラへのアクセス | Unitree SDKとは別である．実際のカメラと対応バインディングを確認する |
| ROS 2 | 任意のセンサー処理，SLAM，記録，可視化 | 必要な依存先が決まってから追加し，既存の内蔵サービスは維持する |
| Docker | アプリケーションの依存環境をまとめ，再現しやすくする | ホスト調査後に互換イメージを検討する．ロボットを制御する通信方式ではない |

コンテナ化しても，ホストのGPUドライバを置き換えたり，任意のCUDA／PyTorch／ZEDの組合せを
互換にしたりはできない．導入済み環境にイメージを合わせ，必要なGPU・カメラへのアクセスを
設定する．同梱のDockerfileはベースの明示が必要なテンプレートである．
[NVIDIAのJetPack手順](https://docs.nvidia.com/jetson/jetpack/install-setup/index.html)と
[StereolabsのJetsonコンテナ手順](https://docs.stereolabs.com/docs/integrations/docker/install-on-nvidia-jetson)を参照する．

研究室の機器では，研究者に割り当てたホストのLinuxアカウントを使う．現在のアカウントが
その用途なら追加は任意だが，以前の利用者のものなら研究用のログインを新しく作る．複数人で
使う場合は，ログインと認証IDを各自で分ける．通常のOpenSSHでは各自のSSH鍵を使い，
[Tailscale SSH](https://tailscale.com/docs/features/tailscale-ssh)ではtailnetのIDとポリシーで認証する．普段は通常の権限を使い，必要な作業だけ管理者
権限で行う．新しいログインはホームと認証情報を分けるもので，OSやシステムのドライバを
分離するものではない．ホストのログインユーザーとコンテナ内のユーザーも別の設定である．
[Ubuntuのユーザー管理](https://ubuntu.com/server/docs/how-to/security/user-management/)を参照する．

開発ではMacからJetsonへのSSHを優先し，直接接続した画面・キーボードを初期設定と復旧に
使える状態にする．SSHサーバーはJetsonのホスト上で動かす．通常のLAN／Wi-Fiで相互に到達
できればVPNは不要であり，VPNは遠隔地や分離されたネットワークからの接続で必要に応じて
使う．同じWi-Fiでも，端末間通信の制限やファイアウォールによって到達できないことがある．
必要なら研究室で認められたVPNを管理用経路に使う．この構成ではJetsonへ到達すればよく，
機体サブネットをVPNへ公開する必要はない．VPNはSSHや，JetsonとB2間の有線DDS接続の
代わりではない．[UbuntuのOpenSSH手順](https://ubuntu.com/server/docs/how-to/security/openssh-server/)を参照する．

Wi-Fiと機体向けEthernetは同時に有効にできる．管理・インターネット用の経路を維持し，
サブネットの重複を避け，機体用インターフェースを明示する．機体側アドレスは研究室または
メーカーの実際の仕様に従い，B2側へ不要な既定経路を追加しない．物理的な接続先は対応する
B2側のEthernetネットワークであり，内蔵Jetsonのアプリケーションへ直接つなぐとは限らない．
内部の経路は引き続き調査する．

ホスト調査 → アカウントとローカルSSH → 任意のVPN → GPUと互換環境の確認 → SDKの依存先と
オフラインモデル推論，の順に進める．保存画像と，テスト用であることを明示した合成状態があれば，
B2なしでソフトウェアを試せるが，モデルファイルと利用が認められた入力は別途用意する必要がある．
机上のJetsonにZEDを接続できれば，カメラもそこで確認できる．実際のB2の状態取得・制御，
機体に残るセンサーとの接続，取付け位置の変換，通信断，自律動作は，実機での結合が必要である．
管理用SSHとホストの構成は確認できた．アプリケーションの実行環境，モデル読み込み，機体との
結合は未検証である．

## 外付けJetsonで最初に取得する情報

SSHによる遠隔調査を実施した．[確認済み構成](target-baseline.ja.md)を参照する．以下は
手動で確認する場合の代替手順であり，**外付けJetson自身のLinux端末**で実行する．
プロジェクトのコピーは不要である．

```sh
cat /etc/os-release
cat /etc/nv_tegra_release
ip -br address
ip route
bridge link
```

ファイルやツールがなければ，その事実を記録する．結果を隠すためのインストールはしない．
ローカル設定の読み取りだけで，機体への要求やネットワークの変更は行わない．外付けJetsonの
Ethernetケーブルの接続先，Macの接続方法，B2の電源状態も記録する．コマンドの出力だけでは，
ケーブルの先や内部の全コンピューターまでは特定できない．

最新版のプロジェクトがあれば，任意の詳細調査を一度に実行できる．

```sh
python3 tools/inspect_target.py --include-network --output local/external-jetson-01.json
```

任意のネットワーク情報には，アドレスのプレフィックス，リンク状態・所属先，IPv4の経路表，
ブリッジのポート，既存の近隣キャッシュ，転送・フィルタリングに関する一部のカーネル設定を
追加した．ping，サブネットの走査，相手へのログイン，パケットキャプチャ，ファイアウォールの
変更は行わない．ツールがない場合やJSONを認識できない場合も明示する．調べられるのは現在の
ネットワーク名前空間なので，物理接続を調べる場合はコンテナ内ではなくJetsonのホスト側で
実行する．IP／MACを含むため，Git対象外の`local/`に保管し，共有前に確認する．生の出力や
認証情報は公開文書にコミットしない．

## 独立した完了条件で進める

| 段階 | 作業 | 完了の証拠 |
|---|---|---|
| 1．実体と配線 | 外付けJetsonの調査，ケーブルの両端と既存の管理方法の特定 | OS／L4Tの記録と，役割・インターフェースの接続図 |
| 2．経路 | 資料で確認したサービスのアドレス・サブネットと，実際に使うインターフェースの特定 | ローカルの経路照会と根拠のある経路．固定IPの無条件な流用はしない |
| 3．状態受信のみ | ホスト上のSDK購読器でインターフェースとドメインを明示 | 有限で更新される状態，トピック，周期，対象機体の確認 |
| 4．センサーと内部サービス | ZED RGBの取得，必要に応じた既知の内蔵サービスの調査 | 実際の映像の出所，座標系，時刻，内蔵サービスへの依存の特定 |
| 5．実行環境の選定 | ホストでの確認後にネイティブ環境または互換コンテナを選ぶ | 選んだ環境でも同じ状態・画像が届き，時刻も確認できる |
| 6．制御と推論 | 制御権・停止手順の確認後に管理下の指令試験，オフライン推論と指令を送らないライブ推論 | 物理動作，モデル実行，その後の自律結合を別々に確認した記録 |

資料で接続先がわかったら，`ip route get ROBOT_SERVICE_IP`でLinuxが選ぶ経路を調べられる．
実際のアドレスへ置き換える．この照会だけでは，相手が存在するとは確認できない．その後に
既知で接続が認められた相手へ回数制限付きpingを行えば，ICMPの到達性を試せるが，DDSの
検証にはならない．pingだけでサービスを識別したり，最初からサブネットを走査したりしない．

DDSには対象のアドレスを持つインターフェースを選ぶ．物理ポートがブリッジのメンバーなら，
IPは物理ポートではなくブリッジに付いている場合がある．`eth0`，インターネット向けの既定経路，
Dockerの仮想インターフェースを自動的に選ばない．プレフィックスと経路の重複を調べる際も，
現在使える管理用接続は維持する．

実際のインターフェースとドメインがわかったら，既存の観測専用コマンドを使う．

```sh
PYTHONPATH=src timeout -k 5s 15s python3 -m b2_tic_vla state \
  --interface IFACE --domain-id DOMAIN_ID --seconds 3 --output local/state-01.json
```

通常と低頻度のsport状態トピックを購読する．Go2-Wで見つかった名前を，B2の挙動の証拠に
しない．調査中は候補指令の送信元を接続しない．公開サンプルは，名前にtestがあっても観測
専用とは限らず，初期化の一部で移動を始めるものもある．

ROS 2は必要な依存先が決まってから追加する．Dockerが必要になった場合もネットワークを
再確認する．Linuxのhostネットワークはホストのネットワーク名前空間を共有するが，
Docker Desktopには異なる制約がある．Mac上のコンテナとJetson Linuxで同じになるとは
仮定しない．[Dockerのhostネットワーク文書](https://docs.docker.com/engine/network/drivers/host/)を参照する．

## 研究室ネットワークを公開せずに結果を残す

実際のアドレス・インターフェース・サービスの対応表は，承認されたローカル保管先に置く．
公開するのは役割名を使った図である．各接続には物理ケーブル，インターフェース，サブネット，
選ばれる経路，観測したサービス，確認日を記録する．サービスごとに，動作ホスト，プロトコル・
ドメイン・トピック，利用側，指令の制御権を区別する．ホストや資料で確認するまでは，推定した
役割を推定のまま残す．実機の証拠が得られたら[進捗](status.ja.md)を更新する．
