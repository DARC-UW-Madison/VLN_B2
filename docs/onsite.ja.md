# 現地での確認手順

[English](onsite.md) · [ホーム](../README.ja.md)

Jetsonの前で，この順に進めます．SSHやGitHubのURLは不要です．報告された構成は
**B2（車輪なし），Jetson AGX Orin，ZED 2i，Livox Mid-360**です．外付けホストの構成と
管理用SSHは[確認済み構成](target-baseline.ja.md)に記しています．センサー・アプリ環境の動作，
B2の配線と制御は未確認です．以下は観測またはオフライン処理のコマンドで，
このリポジトリには現時点で**モーターへ指令を送るコマンドはありません**．


外付けJetsonと別の内蔵コンピューターを扱う場合は，
[計算機の役割とネットワーク調査](network-topology.ja.md)から始め，SDKのサービスを試す前に
配線と経路を特定する．

## 1．プロジェクトを持参し，Jetsonを調べる

USBメモリなど研究室で認められた方法でリポジトリをJetsonにコピーし，ルートフォルダで
端末を開きます．`git archive`で書き出したソースのみのアーカイブなら，Git履歴，ローカルの
記録，仮想環境を含めずに持参できます．Jetsonで展開し，プロジェクトのルートに移動します．
別のコンピューターの仮想環境はコピーしません．OSがまだ使える状態で
なければ，モジュールとキャリアボードの型番，ストレージを先に記録します．既存の状態を
調べてから，対応するJetPackイメージや書き込み方法を選びます．

```sh
python3 tools/inspect_target.py --output local/target-inventory.json
```

この単独スクリプトはPython 3.8以上と標準ライブラリだけで動きます．OS，アーキテクチャ，
メモリ，空き容量，L4T／JetPack・CUDA・TensorRTのパッケージ情報，Pythonパッケージの
バージョン，Dockerの標準ローカルソケット，USB機器IDを調べます．インストール，SDKの
読み込み，ロボット指令，sudoの使用は行いません．`unknown`や`not_checked`は追加確認が
必要という意味で，ロボットの故障とは限りません．ネットワークへの要求は行わず，Dockerも
標準のローカルUnixソケットだけを調べます．各コマンドに制限時間があるため，全体では
複数回分の制限時間がかかることがあります．

標準出力からは，ホスト名，ユーザー名，IP／MACアドレス，シリアル番号，コマンドの生の
診断出力を除外します．このレポートもGit対象外の`local/`に保存し，共有前に内容を確認
します．任意のネットワーク調査ではインターフェース名，IP／MACアドレスが含まれるため，
結果をローカルに保管します．

```sh
python3 tools/inspect_target.py --include-network --output local/target-network.json
```

既存のSDKのチェックアウトが見つかった場合は，コピーせずにリビジョンを調べられます．

```sh
python3 tools/inspect_target.py --sdk-path /path/to/unitree_sdk2_python --output local/target-sdk.json
```

`/path/to/...`は実際の場所に置き換えます．記録するのはリビジョンと変更の有無で，
ローカルのパスや変更されたファイル名は含めません．

## 2．依存環境を確認し，カメラとB2を別々に試す

プロジェクト本体はPython **3.10以上**が必要です．まず`python3 --version`で確認します．
このパッケージのためだけにシステムPythonを置き換えたり，JetPackを更新したりしません．
導入済みのベンダーバインディングを読み込める互換環境を使います．本体を実行できなくても，
前述の調査スクリプトは使えます．

それぞれの確認に必要なものは次のとおりです．

| 確認 | 事前に必要な実行環境 | 成功時の観測 |
|---|---|---|
| カメラ | 公式ZED SDKと`pyzed.sl`，USB接続 | 左側の補正済み映像が写った空でないJPEG |
| B2の状態 | 公式`unitree_sdk2py`，CycloneDDS，実際のB2接続インターフェース | JSONに有限値の状態と受信トピックが記録される |
| モデル | 対応するJetson版PyTorch／CUDA，上流TIC-VLA環境，ローカルの基盤モデルと重み | オフライン推論で有限値の将来XY点列が得られる |

研究室の既存環境を優先します．不足があれば，調査結果と公式手順から対応バージョンを
選んで導入し，該当する確認を再実行します．`pyenv`だけではNVIDIAのライブラリやベンダー
バインディングは揃いません．ホストの構成情報だけではアプリ用パッケージの互換性やセンサーの
動作を確認できないため，一括インストールは用意していません．

Jetson Linuxでは，プロセスの制限時間を付けてカメラを試します．ネイティブドライバが
Pythonの再試行制限を超えて停止する場合に備え，外側の`timeout`でも制限します．

```sh
PYTHONPATH=src timeout -k 5s 30s python3 -m b2_tic_vla camera --output local/camera-01/frame.jpg
```

`local/camera-01/frame.jpg`を現地で開き，実際の前方が正立・合焦して写り，カメラの取付けが
固定されていることを確認します．隣のJSONには，カメラ由来の時刻とホスト受信時刻を別々に
保存します．**撮影時刻とホスト時計の対応は未検証**です．深度と自己位置追跡は無効で，
この確認からZEDの追跡・深度モデルを要求することはありません．他のカメラアプリは先に
閉じてください．

B2については，任意のネットワーク調査結果または`ip -brief link`から，機体につながる
有線インターフェースを確認します．以下の`IFACE`を置き換えます．Go2-Wのアドレスや
インターフェースを推測で流用せず，研究室の配線・アドレス設定に従います．無関係な
ネットワーク設定は変更しません．

```sh
PYTHONPATH=src timeout -k 5s 15s python3 -m b2_tic_vla state --interface IFACE --seconds 3 --output local/state-01.json
```

`auto`は`rt/sportmodestate`と`rt/lf/sportmodestate`の両方を購読します．JSONには受信数と
有効な状態の取得元トピックが記録されます．DDSの探索通信は発生しますが，制御クライアント
や移動指令の送信者は作りません．`velocity_frame`と`frame_id`は`unknown`のままです．
受信成功だけでは，軸，単位，制御の準備状態を確認したことにはなりません．有効な状態が
なければ，診断結果を保存したうえで終了コード2を返します．

既存ファイルは上書きしません．試行ごとに番号を変えてください．失敗時に画像や未完成の
観測フォルダが残る場合は，診断用に保管し，再試行には新しいフォルダを使います．

## 3．実物が必要な事実だけ記録する

[記録用テンプレート](../examples/onsite-notes.json)をGit対象外の`local/`にコピーします．
ソフトウェアのバージョンは調査レポートから得られます．以下は実物や研究室の既存マニュアルで
確認し，未解決の欄はnullのまま残します．

| 確認すること | 記録内容 | 必要な理由 |
|---|---|---|
| 計算機と配線 | Orinのメモリ・ストレージ，カメラUSB，機体Ethernet，センサー電源 | 計算資源と基本接続の確認 |
| 既存の手動操作 | 現在のアプリ・コントローラー，通常停止，操作者による介入，稼働サービス | 既に使える操作・停止手段の把握 |
| 制御権と通信断 | 制御しているプロセス，指令・接続喪失時の仕様と後日の実測 | ホストの期限判定は通信断後の機体を停止できないため |
| 座標系 | SDK速度の座標系，x／y・旋回の符号，位置の座標系，単位 | 正常なメッセージでも解釈を誤る可能性があるため |
| カメラ配置と時刻 | 機体に対する高さ・向き，前方の視野，撮影時計の起点とバッファ | 学習時の視点との差，画像の遅延の評価 |
| ローカル推論 | GPUメモリ，処理時間，温度，上流コード・重みの対応リビジョン | 想定する実行周期の実現性の確認 |

初回訪問でモデルによる移動試験をする必要はありません．移動を伴う座標・停止の確認は，
研究室の操作者と既存の手動手順で行います．SDKのメソッド名やGo2-Wの記録だけから，
通信断時の挙動を推測しません．LiDARとROS 2は別の追加確認です．RGB画像とB2の状態を
取得する段階の必須条件にはしません．背景は[導入情報](deployment-intake.ja.md)を参照します．

## 4．画像と状態を組にして保存する

二つの確認が通ったら，時刻の近い状態と画像を保存します．

```sh
PYTHONPATH=src timeout -k 5s 30s python3 -m b2_tic_vla record --interface IFACE --output-dir local/observation-01
```

`frame.jpg`と`observation.json`を作ります．受信時刻の差を0.2秒以下に制限していますが，
これは記録の整合性を見るための例示値で，センサー同期の検証ではありません．由来の異なる
時計と未確認の座標系は，未確認として保存します．SDKの速度座標系を確認した後に限り，
新しい記録で`--velocity-frame body`または`base_link`を指定します．`--position-frame`には
確認済みの位置座標系の名前を記録できます．いずれも測定値へのラベル付けで，座標変換は
行いません．確認前はunknownのままにします．

## 5．準備済みのオフライン推論を試す

重みと上流ソースは同梱していません．取得前に，上流の利用条件，固定するリビジョン，
容量，保存先，研究室のアクセス規則を確認します．公式のキャッシュと取得ツールを使い，
このリポジトリで重みを再配布しません．独自コードと文書のMITライセンスは，
これらの外部資産を対象にしません．[第三者資料の条件](../THIRD_PARTY.ja.md)を参照してください．

対応する上流環境とローカルのファイルが揃っても，先に
[チェックポイント読込の制約](runtime-compatibility.ja.md#検証範囲を限定したビルド案)を解決します．
旧PyTorchのビルド候補はモデル不要の確認専用で，`weights_only=True`だけでは公表済みの脆弱性を
解決できません．修正または代替の読込経路を検証するまで，その候補で外部チェックポイントを
読み込みません．その後，以下のパスを全て置き換えます．
内容を確認してリビジョンを固定した上流チェックアウトを使います．プロセスの読み込み先に
加えますが，このプロジェクトへコピーはしません．

```sh
PYTHONPATH=src python3 -m b2_tic_vla infer \
  --observation local/observation-01/observation.json \
  --velocity-frame body \
  --instruction "Walk toward the open doorway." \
  --base-model /path/to/local/InternVL3-1B \
  --checkpoint /path/to/local/TIC-VLA-model.ckpt \
  --upstream-root /path/to/local/TIC-VLA \
  --output local/plan-01.json
```

座標系の上書きは速度の規約を確認した場合だけ使います．Hugging Faceはローカルのみを
読み込み，`torch.load(weights_only=True)`と厳密な重みの照合を使います．不一致時に重みを
黙って除外したり，制限のないpickle読み込みへ切り替えたりせず，エラーにします．上流や
モデルに含まれるローカルPythonコードは実行されるため，信頼性の確認が必要です．
オフラインの読み込み設定はコードを隔離する仕組みではありません．

これは**保存データの同期推論**であり，TIC-VLAの非同期ライブシステムではありません．
遅延と相対変位をゼロとし，再生用にホスト時刻を取り直します．元の観測メタデータは別に
保持します．現在のパッケージが返すXYは，現在の機体座標系に対する将来位置なので，
**累積和は取りません**．出力する処理時間は予測の所要時間で，撮影から機体応答までの
全遅延ではありません．一度もっともらしい経路が出ただけで検証済みとせず，異なる指示と
場面で確かめます．

## 6．測定結果から次の実装を決める

- カメラが失敗する場合は，USB・電源と導入済みZED SDKの公式診断から確認します．
- 状態が来ない場合は，実際のインターフェース，配線・アドレス，SDKのリビジョンと実行環境を
  確認し，レポートを残します．別機体向けのSDK改変を無条件に流用しません．
- モデルが失敗する場合は，エラーをローカルに残し，上流コード・基盤モデル・重みの対応，
  アーキテクチャ，GPU用ビルド，メモリ，Pythonバインディングを切り分けます．
- 全て通ったら，参照時刻・姿勢と一体の非同期キャッシュ，時計・座標の整合，指令を送らない
  ライブループを実装・検証します．停止，介入，通信断時の挙動，実測遅延に基づく制限値を
  確認してからB2への指令送信を有効にします．これらは今後の結合作業です．

同梱の[Dockerfile](../deploy/Dockerfile)は，必要なPython環境を含む`BASE_IMAGE`の明示が
必要です．ホストのL4Tに合うJetsonイメージを選びます．任意のイメージでZEDとPyTorchが
共存するとは仮定しません．このテンプレートはインストールを行わず，標準動作はヘルプ表示
です．Jetsonでのビルドは未検証です．カメラ・GPUへのアクセスとDDSのネットワークは
現地で別途設定する必要があり，ビルド成功だけでは確認できません．
[StereolabsのJetson Docker手順](https://docs.stereolabs.com/docs/integrations/docker/install-on-nvidia-jetson)と
[NVIDIAのコンテナ資料](https://developer.nvidia.com/embedded/jetson-cloud-native/)を参照します．

既存の互換ベースを選んだ後のビルド形式は以下です．

```sh
docker build --build-arg BASE_IMAGE=YOUR_MATCHED_IMAGE -t b2-tic-vla:local -f deploy/Dockerfile .
docker run --rm --network none b2-tic-vla:local replay
```

二つ目のコマンドは合成データの再生だけを行い，ロボット，GPU，カメラ，ネットワークは
不要です．推論用の配備イメージの検証にはなりません．
