# 開発と実験の手引き

[English](development.md) · [ホーム](../README.ja.md)

B2で再現可能な実験を行うまでの進め方を説明する．完了しているのはリポジトリの準備だけである．
後続の段階は完了条件を定義したもので，動作確認済みのインストール手順や実機制御手順ではない．

## 1. システムを理解する

[構成と仕組み](architecture.ja.md)と[進捗](status.ja.md)を読む．
チェックポイントとは保存されたモデルのパラメータである．推論はそのパラメータを使って予測を行う処理であり，学習ではない．
軌道は時刻に対応する位置を指定し，速度指令は現在どれだけの速さで動くかを指定する．
接続部では，確認済みの単位と座標系を使って両者をつなぐ必要がある．

図に描いた軌道がもっともらしいだけでは，ナビゲーションの成功とはいえない．
ロボットが軌道を実行し，新しい観測に反応し，意図した目的地に到達する必要がある．
以下の段階では，これらの問いを個別に確かめてから組み合わせる．

## 2. 実際の環境を特定する

モデルの依存パッケージを導入する前に，以下を環境仕様としてまとめ，レビューする．
接続先アドレスと認証情報は研究室の管理領域に置く．
詳しい確認項目，読み取り専用の調査コマンド，最初の回答用テンプレートは
[導入前に集める情報](deployment-intake.ja.md)を参照する．

| 項目 | 必要な情報 | 確認する理由 |
| --- | --- | --- |
| 機体 | B2の型式，ファームウェア，利用可能な高位API，停止と介入の挙動 | 制御の接続条件を決める |
| 計算機 | CPUアーキテクチャ，GPUとメモリ容量，OS，ドライバー，CUDAまたはJetPack | 互換性のある推論環境を選ぶ |
| カメラ | ドライバー，画像形式，解像度，周期，時刻，校正，取り付け位置の変換 | モデルの観測を機体に対応させる |
| 機体状態 | 取得可能な速度・位置・姿勢，座標系，周期，時刻 | 推論中の移動を復元する |
| 通信 | SDKの版，接続方法，時計の対応，実測した遅延 | 観測の不一致や古いデータの混入を防ぐ |

Linuxの対象機では，次の読み取り専用コマンドを環境確認に利用できる．

```sh
uname -m
cat /etc/os-release
python3 --version
nvidia-smi
```

これらは対象機ではまだ実行していない．Jetsonでは `nvidia-smi` が利用できない場合があるため，
導入済みのプラットフォーム用ツールからJetPackとGPUの情報を取得する．共有前に出力内容を確認する．
別のロボットの手引きからB2の構成を推定しない．ROS 2の必要性を確認してからディストリビューションを選ぶ．

**完了条件：** 非公開のチャットを読まなくてもハードウェアとソフトウェアを特定でき，
未確認事項ごとに次の確認方法が決まっていること．

## 3. オフラインでモデルの推論を再現する

先に[外部資料の利用条件](../THIRD_PARTY.ja.md)を確認する．上流のコミット，モデル配布元の版，
チェックポイントのチェックサム，依存パッケージの版，数値精度，入力の前処理を記録する．
外部資料は，公式の配布ツールを使い，このリポジトリとは別に取得する．

研究利用が認められた小さな記録を使う．画像の取得時刻と，対応する機体状態のサンプルを保持し，
座標系と単位を調べる．チェックポイントを読み込み，不足・余分なパラメータがないか調べ，
行動出力の形と意味を確認する．チェックポイントの不一致は設定の失敗であり，無視してよい警告ではない．

予測軌道を観測に重ねて確認する．初期化，定常状態の推論，観測の古さを別々に測り，GPUメモリ使用量を記録する．
画像欠落，機体状態の欠落，結果の遅延，不正な数値出力を試す．
プログラムは失敗を報告し，実行可能な指令を出さないこと．

**完了条件：** 指定した入力と版から，別の研究者が予測を再現できること．実機の移動インターフェースは接続しない．

## 4. 移動指令を送らずに実機の予測を確認する

実際のカメラと機体状態の取得部を接続し，指令送信は無効のままにする．
承認された手動操作の手順で静止，直進，旋回の観測を集めて比較する．
画像と状態の時刻対応，カメラから機体への座標変換，キャッシュの時刻，予測の古さを確認する．

遅い推論や一時的なセンサー停止も含める．古い出力を現在のものとして示さず，期待する状態を報告するか確かめる．
確認用の出力には，取得時刻，予測時刻，座標系と単位，候補の指令，その指令を採用・拒否する理由を表示する．

**完了条件：** 変換と指令の拒否が正しいことを記録で示せること．この段階だけでは自律走行性能を確認したことにならない．

## 5. 指令経路を検証してからナビゲーションを評価する

モデルによる指令を有効にする前に，実験区域，操作者の制御，速度・加速度の上限，停止距離，復旧手順を決める．
実際のファームウェアでSDKの戻り値と指令途絶時の挙動を確認する．
指令の失効と停止の処理はモデル推論から独立させる．SDKの呼び出し成功だけでは，機体が停止した証拠にならない．

管理された環境で接続部と軌道追従の試験を行い，合格後に短距離のナビゲーションに進む．
設定の調整と評価を分け，比較実験の前に課題，試行数，上限，成功条件を定義する．
手動介入，異常，衝突，不成功を含め，試みたすべての試行を記録する．

目的地への到達，介入，経路長，遅延の分布，停止動作，計算資源の使用量を測る．各指標の定義と分母を明記する．
条件をそろえて，仕様を明示した比較対象と比べる．別の機体や環境で発表された結果を代用しない．

**完了条件：** 方法，全試行の内訳，結果，失敗の分析，証拠から主張できる範囲を報告できること．

## 再現できる記録を残す

各実験について，以下を記録する．

- 問い，仮説，比較対象，事前に決めた判定基準．
- コードのコミット，モデル・チェックポイントの版とチェックサム，パッケージ・ファームウェアの版，
  ハードウェア，校正，設定，該当する場合の乱数シード．
- 入力データの版，指示文，手順，時刻，試行数．
- 測定結果，失敗，計画からの変更，分析方法，不確かさ．
- 承認された保管先にある証拠の場所とアクセス条件．公開する報告には，非公開の保管先アドレスや個人を特定できる録画を含めない．
- 結論，制限，結果を根拠に選ぶ次の実験．

生の録画，地図，モデルファイル，実行ログは研究室が認める保管先に置く．
コミットするのは，公開可能な内容に整理した報告，設定例，小さな合成データなど，共有を認められたものだけとする．
無視パターンは作業を助ける仕組みであり，新しいファイルを公開してよいという保証ではない．

## 確認に失敗したとき

| 観測された問題 | 次に調べること |
| --- | --- |
| チェックポイントのキーやテンソルの形が合わない | コードの版，モデル設定，チェックポイントを照合し，接続作業を止める |
| 直進するはずの軌道が曲がる，または左右反転する | 軸，旋回角の符号，カメラの座標変換，増分の合成方法を調べる |
| 予測が遅れて見える，または不連続になる | 取得時刻，時計の対応，キャッシュの交換，キュー内のデータの古さを追う |
| SDKは指令を受け付けるが機体の動きが違う | 承認された手順で，ファームウェア，制御モード，単位，指令の制御権を確認する |
| 結果を再現できない | 調整を始める前に，版，入力，校正，乱数シード，試行の定義を比較する |

原因と修正の確認結果を該当する手引きに記す．次の段階に進めるようになったら，
両言語の文書と[進捗](status.ja.md)を更新する．
