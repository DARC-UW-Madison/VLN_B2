# ビルドで何を作り，どう実行するか

[English](build-fundamentals.md) · [実際の構築](jetson-runtime.ja.md) · [実行の流れ](runtime-flow.ja.md)

## 最初に扱うものを分ける

CPUは機械語の命令を実行する．ソースコードは，人が編集できる形で書いたプログラムである．
コンパイラーが対象の機械向けの命令へ変換し，ビルドが変換・結合・梱包をまとめて進める．
インストールは，その結果をアプリから使える場所へ配置する．実行は，プロセスを起動して処理を行う．
学習はモデルの数値を更新し，推論はその数値を使って入力から出力を計算する．
今回の長いビルドで作ったのはソフトウェアであり，ナビゲーションを学習した重みではない．

| 対象 | 本プロジェクトでの意味 |
|---|---|
| ソース | 動作を記したPython・C++・CUDAのファイル |
| オブジェクトファイル，主に`.o` | 個別にコンパイルした部品．通常は他の部品と結合する前のもの |
| 実行ファイル | OSが起動できるプログラム．Python本体や今回のCUDA検査など |
| 共有ライブラリ，Linuxでは`.so` | 他のプログラムから読み込むコンパイル済みの機能 |
| wheel，`.whl` | Pythonパッケージのインストール用アーカイブ．Pythonとコンパイル済みの部品を含む場合がある |
| モデルの重み | 学習した数値のテンソル．PyTorchのコンパイルでは作られない |
| Dockerイメージ | 層を組み合わせて保存したアプリ用ファイルシステムと設定 |
| コンテナ | ホストのカーネルを共有し，プロセス・ファイルシステムの名前空間を分けた実行単位 |

## Pythonなのにコンパイラーが必要な理由

通常のCPythonは`.py`をバイトコードへ変換し，インタープリターで実行する．`.pyc`のキャッシュは，
単独で起動できるARMの実行ファイルではない．Python本体もコンパイル済みのソフトウェアである．
さらに，Pythonパッケージはコンパイル済みの拡張を読み込める．`torch._C`はPythonから
ネイティブのTorch機能へつなぐ部分で，Pythonが窓口となり，重い演算はC++やGPUのライブラリで行う．
[CPythonの拡張モジュール](https://docs.python.org/3.11/extending/building.html)を参照する．

```text
Python application
  -> Python package / native extension
  -> compiled CPU code and operation dispatcher
  -> CUDA libraries or compiled GPU kernels
  -> host NVIDIA driver
  -> GPU
```

CUDAのテンソルで行列積を呼ぶと，GPUへ仕事を渡す．CPUは引き続きPythonや仕事の投入，データの管理を行う．
OrinでCPU・GPUが物理メモリを共有していても，テンソルのデバイス指定や同期が不要になるわけではない．
GPU処理は非同期の場合があり，CPUが仕事を投入した時間だけでなく，完了まで待って測る必要がある．

## コンパイラー，リンカー，ビルドシステム，パッケージ管理

ネイティブコードの大まかな流れは次のようになる．

```text
.cpp -> C++ compiler -> .o files --+
                                +-> linker -> executable / .so -> wheel -> install
.cu  -> nvcc -> CPU/GPU objects --+
```

コンパイラーは個々のソースを検査・変換し，リンカーは部品を結合して，他の関数・ライブラリへの参照を解決する．
ヘッダがない場合は主にコンパイルの問題で，未解決のシンボルは結合時や読込時の問題になり得る．
Pythonモジュールがない場合は，さらに別の層である．失敗した層を分けると，関係のないパッケージを
繰り返し変更することを避けられる．

CUDAのソースにはCPU側の処理とGPUの関数が混在する．`nvcc`がCPU用コンパイラーやGPU用の変換を
取りまとめる．CUDAカーネルのコンパイルは通常CPU上のコンパイラープロセスで行い，GPUが学習しているのではない．
[CUDA 11.4のコンパイラー資料](https://docs.nvidia.com/cuda/archive/11.4.0/cuda-compiler-driver-nvcc/index.html)を参照する．

CMakeは依存先を調べて，どの部品をどう作るかというビルドのグラフを生成する．Ninjaはそのグラフに従って
コンパイル・結合のコマンドを実行する．CPythonの構築ではconfigureとMakeを使った．
pipはPythonパッケージを導入し，適した完成品がなければパッケージのビルド処理も呼び出せる．
wheelのインストールでコンパイルが省けるのは，事前に他の場所で行った結果が入っているためである．

## このJetsonへ任意のwheelを入れなかった理由

コンパイル済みパッケージは，複数の条件を合わせる必要がある．

| 境界 | 今回の対象 |
|---|---|
| CPUの方式 | Linuxのaarch64．x86-64のPC用ではない |
| OS・ネイティブABI | Linuxのライブラリの接続規約．ARMのMac用パッケージでもLinux用とは異なる |
| Python拡張のABI | 今回のアプリ環境ではCPython 3.11 |
| CUDA・ツール・ドライバ | 調査したL4T 35.4.1・CUDA 11.4の世代 |
| GPUの命令対象 | Orinのcompute capability 8.7．`sm_87`や`8.7`で指定 |
| ライブラリ同士の接続 | Torch・visionと，他のネイティブ依存先の整合 |

wheelのタグはインタープリター・ABI・プラットフォームを表す．
[Pythonパッケージの仕様](https://packaging.python.org/en/latest/specifications/platform-compatibility-tags/)を参照する．
該当するタグの`cp311`はCPython 3.11を示すが，そのタグだけでCUDA・ドライバの全条件を保証しない．
compute capability 8.7も，CUDAのバージョン8.7という意味ではない．

調べたNVIDIAのJetPack 5用wheelはPython 3.8向けで，本家アプリはPython 3.10以上を要求する．
pyenvはインタープリターを変えるが，Torchの再構築やGPUドライバの交換は行わない．
このため，既存ホストに対してソースビルドの候補を検証した．常にすべてをソースから作るべきという意味ではなく，
互換性と条件を確認した完成品があれば，通常はそちらが簡単である．正確な制約と，旧Torchの重み読込の
未解決の問題は[互換性調査](runtime-compatibility.ja.md)に記す．

## 今回完了したビルドの具体的な内容

1. **対応する基底イメージを使う．** 版を固定したNVIDIAのARM64用L4Tイメージを，互換性のある
   ユーザー空間・開発ツールの土台にする．ホストのカーネルとドライバを使う．
2. **Pythonを作る．** 検査したCPythonのソースを取得し，`/opt/python`への配置を設定して，
   4並列でコンパイル・導入する．研究用ログインにも別のホスト用Pythonを作ったが，同じ実体ではない．
3. **Torchを作る．** 指定した版とsubmoduleを取得し，CMake・NinjaでC++・CUDAをコンパイルして
   Orin向けのwheelを作る．そのwheelをイメージ内のPythonへ導入する．2093件の表示はコンパイル・結合などの
   対象数であり，学習回数や全作業の完了率ではない．
4. **torchvisionを作る．** そのTorchに対して，選んだ画像処理用パッケージをコンパイルする．
   バージョン番号を合わせるだけでなく，ネイティブの部品も整合させる．
5. **推論用の依存先を入れる．** Transformers，Lightningなどを導入する．コンパイル後にビルド専用の
   CMake・Ninjaのwheelを外し，残りの依存関係を検査して記録する．
6. **イメージを仕上げて試験する．** `vln-b2-runtime:jp5`として保存し，実際のOrin GPUを使う
   オフラインの検査用コンテナを起動する．

`MAX_JOBS=4`は，同時に動かすコンパイラーの数を制限して資源消費を抑える指定である．
GPUのコア数，ロボットの台数，推論の速さを示すものではない．Torchは大量のネイティブコードと
GPUカーネルを含むため，コンパイルに時間がかかる．

候補ではTensorPipe RPCを省いたが，Python側の判定がそれを読もうとしたため，ソースのハッシュを確認して
機能の判定だけを修正した．Unitreeへの要求とは無関係で，チェックポイントの脆弱性修正でもない．
ビルド専用wheelの情報にも不備があり，コンパイルには使えた後，最終の依存検査前に外した．
[実際の復旧と確認結果](jetson-runtime.ja.md#torchのimport判定とビルドの再開)を参照する．

## Dockerのビルドと，コンパイラーのビルドの範囲

イメージのビルドはDockerfileの指示を実行する処理である．`RUN`ではパッケージ取得，コンパイル，
検査，情報の保存などを行える．一回のDockerビルドの中に，複数のソフトウェアのビルドが含まれる．

| 指示 | 今回の使い方 |
|---|---|
| `FROM` | 基底イメージ・段階を選ぶ |
| `ARG` | 固定した版などのビルド時の値．秘密情報の保存先ではない |
| `ENV` | 後続の構築・コンテナ実行に残る環境変数 |
| `RUN` | イメージを作る段階で導入・コンパイル・検査を実行する |
| `COPY` | 許可した入力ファイルをイメージへ入れる |
| `CMD` | 後でコンテナを起動する際の既定の処理．記述した時点では実行しない |

[Dockerfileの資料](https://docs.docker.com/build/concepts/dockerfile/)を参照する．
`docker build ... .`の最後の`.`は，`COPY`などの入力を取る場所，ビルドコンテキストである．
`.dockerignore`で個人用・ローカルのファイルを除外する．保存されるのはイメージのファイルの変更であり，
実行中のPythonや読込済みのモデルのメモリではない．`docker run`で後から新しいプロセスを起動する．

変更のないビルドの層は再利用できる．早い段階の入力を変えると，後のキャッシュも使えなくなる場合がある．
頻繁に変える文書を長いコンパイルより前にコピーすると，無駄な再コンパイルの原因になる．
今回は完成済みのTorchイメージを残し，ビルド引数も維持して残りのレシピを生成した．
[キャッシュの無効化](https://docs.docker.com/build/cache/invalidation/)を参照する．
SSHを開いたり，完成済みイメージを起動したりするたびに，コンパイラーを動かすわけではない．

## 全体を追える小さな具体例

既存の`deploy/cuda-smoke.cu`は，256個の値について`output[i] = 2*x[i] + y[i]`を計算する．
CPUで入力を用意し，CUDA用の領域を確保してGPUカーネルを投入し，完了を待ってCPUの計算結果と全要素を比較する．
128スレッドのブロックを2個使い，配列外の添字は除く．ニューラルネットワーク，センサー，インターネット，
ロボットに依存せず，プログラムの構築と実行を確認できる．

この対象機で既に使用したビルドのコマンドは次のとおりである．

```sh
/usr/local/cuda/bin/nvcc -O2 -arch=sm_87 deploy/cuda-smoke.cu -o local/native-smoke/cuda-smoke
```

`-O2`は最適化，`-arch=sm_87`はOrinのGPU向けの指定，`-o`は出力する実行ファイルの名前である．
コンパイルでファイルを作り，それを起動すると計算を行う．続くTorch検査では，ライブラリの演算を調べた．
どちらも，実際の重みでTIC-VLAを動かすことより狭い範囲の検証である．

## 変更したら何を作り直すか

| 変更 | 通常の対応 |
|---|---|
| ナビゲーションの指示 | 推論の入力を変える．Torchの再ビルドは不要 |
| 互換性のある重み | 条件を確認して読み込む．通常Torchの再ビルドは不要だが，モデルの互換性は検証する |
| 独自のPython接続部 | ソースを更新しプロセスを再起動する．ソースをイメージに含めた場合はアプリ用イメージも再構築する |
| C++・CUDA拡張 | その拡張をコンパイル・結合し，必要なパッケージ・イメージを作り直す |
| Torchのネイティブソース・有効な機能 | 該当するネイティブ部品と，依存する拡張を作り直す |
| JetPack・ドライバ・GPU環境 | 互換性を再評価し，関係する環境を再構築・検査する |

今後の最適化には，量子化，TensorRTのエンジン生成，`torch.compile`，カーネルの特化などもある．
それぞれにハードウェア，数値，時間，成果物の条件があり，今回のビルドで実施した処理ではない．
追加学習はさらに別で，データと目的関数を使い，学習したパラメーターを更新する．

版の固定と基底イメージのdigestは由来の管理に役立つが，今回のレシピは完全な再現性のlockではない．
apt・推移依存や構築条件も関係する．情報と正確な版を残し，正式な研究比較の前には固定を強める．
ビルド成功，import成功，有限なGPU演算，モデル推論の品質，安全な実機動作は，別々の検証である．
