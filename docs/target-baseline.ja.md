# 外付けJetsonの確認済み構成

[English](target-baseline.md) · [進捗](status.ja.md) · [ネットワーク設計](network-topology.ja.md)

**2026-10-27**に読み取り専用の調査を行い，以下の構成を確認した．MacからTailscaleのネットワークを
通したSSHが動作した．準備済みの調査スクリプトは，対象機のPython 3.8へ標準入力で渡して実行した．
この調査ではプロジェクト，パッケージ，モデル，マウント，ネットワーク設定を作成していない．
管理者権限でのDockerメタデータの照会も行った．公開を想定した記録のため，実際のユーザー名，
機器名，アドレス，MAC，シリアル番号，ファイルシステム識別子，認証情報は省いている．

## Dockerとストレージ

Dockerのクライアントとサーバーは**26.1.3**である．管理者権限の照会で，`nvidia`，`runc`，
`io.containerd.runc.v2`の登録と，既定値が`runc`であることを確認した．コンテナ内からGPUを
使えることの証拠ではない．イメージの取得，コンテナ起動，デーモン設定やグループの変更は行っていない．

研究用ログインはsudo／video／renderに属するが，標準のDockerソケットへのアクセス権はない．
権限なしの`docker info --format`は，権限エラーがあるにもかかわらず，空のサーバー情報と
終了コード0を返した．調査ツールはDebianのビルド表記を認識し，Dockerがないという扱いにせず，
ソケットの権限不足を明示するよう修正した．管理者権限での照会は成功しており，コンテナを使う
際の権限は今後明示的に選ぶ．

調査時点のルートファイルシステムは**総量約61 GB，空き約20 GB**である．別に**2 TBのNVMe SSDがあり，ext4
パーティションは未マウント**である．読み取り専用のファイルシステム情報では，空きは約1.05 TB，
割り当て済みは管理領域を含め約0.95 TBで，空のディスクではない．superblockには`clean`と
`needs_recovery`の両方が表示される．これらの値から，ファイルシステムの健全性や既存データを
再利用してよいことまでは確認できない．内容と所有者は未確認で，対応する永続マウント設定はない．
フォーマット，マウント，移動，共有Docker保存先の変更は行っていない．大きな取得を始める前に，
モデルのキャッシュ，イメージ・ビルド，プロジェクトの保存先を決める．新しいホームを作っただけでは，
容量が増えたり別ディスクになったりはしない．

Dockerの照会では，イメージ数と実行中コンテナ数はともに0で，保存先は容量の小さいルート側である．
停止中コンテナとvolumeは未調査である．研究用ログインには，プロジェクトの作業領域と
Hugging Faceのキャッシュはまだない．大きなキャッシュの作成や共有Dockerの変更に進む前に，
既存データを保って保存先を調べる．

## 確認した管理用ネットワーク

| インターフェースの役割 | 観測 |
|---|---|
| Wi-Fi | `wlan0`が有効で，既定経路に使われる |
| Tailscale | `tailscale0`あり．SSH管理を確認済み |
| 機体向け有線ポート | `eth0`は管理上UPだが，キャリアとIPアドレスがない |
| 既存のUSBブリッジ | `l4tbr0`に`rndis0`／`usb0`が属し，今回の調査では無効 |
| Dockerの仮想ブリッジ | `docker0`あり．有効なキャリアは観測されていない |

Wi-Fiを機体へ中継するブリッジ構成ではない．B2の状態，機体のアドレス，サービスのドメイン，
内部スイッチ，内蔵計算機の役割は未確認である．このログインにはDDS／ROSの環境変数が
設定されていなかったが，全サービスや別ユーザーの環境を表すものではない．

## 実行環境の選定に関わる点

本プロジェクトは現在Python 3.10以上を必要とするが，ホストの既定値は3.8.10である．
システムPythonとベンダー環境を維持し，互換性のあるアプリケーション用Pythonまたはコンテナを
選ぶ．単独の調査スクリプトはPython 3.8に対応し，今回，対象機で実行できた．

確認した[上流の学習用依存定義](https://github.com/ucla-mobility/TIC-VLA/blob/main/requirements-train.txt)は
Torch 2.8.0とCUDA 12.8を指定しており，CUDA 11.4のJetsonへの配備手順にはならない．
この学習用の指定から，推論に最低限必要な版や，ホスト更新の必須性までは決まらない．
推論に使う互換性のある組合せは試験が必要である．[互換性調査](runtime-compatibility.ja.md)に
候補と制限を記した．コンテナ化だけで差が解決するわけではない．

## 次の実装順

1. 既存ext4の内容と他のアカウントを保ち，保存先を決める．SSDの用途を確認してから研究用の
   専用ディレクトリを作る．フォーマットはこの計画に含めず，モデルは公式のキャッシュを使う．
2. Jetsonに対応するGPU／Python／PyTorchの候補を選ぶ．現在のOS，ROS，ZEDを維持して試す．
   ホストや起動系の大きな更新には，別途，具体的な移行・復旧計画が必要である．
3. モデル読み込み前に，選んだコンテナのPython，GPU初期化，テンソル演算，資源使用を確かめる．
   この確認は機体動作と区別する．モデルファイルはまだ取得していない．
4. 基盤モデルと重みの取得前に，利用条件，版，容量，キャッシュの場所を確認し，その後に
   利用が認められた入力で同期推論を実行する．
5. 後にB2を資料に従ったEthernetへ接続し，実際のサービスとドメインを特定する．制御へ進む前に
   状態・カメラの時刻を検証する．

ローカルでは，Dockerの解析と権限判定の回帰テストを含む**85件のテストが通った**．修正した
調査ツールは対象機のPython 3.8でも実行した．モデル推論，コンテナのGPU演算，ZED撮影，
B2の制御は引き続き未検証である．
