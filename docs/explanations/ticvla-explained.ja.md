# TIC-VLAの中で画像と指示が経路になるまで

[English](ticvla-explained.md) · [文書目次](../README.ja.md) · [学習の仕組み](ticvla-training.ja.md) · [経路からB2の制御へ](control-loop.ja.md)

> 文書種別：**解説**．モデル内部の計算を順番に追う章であり，起動手順ではない．準備済みの環境を動かすには[カメラのチュートリアル](../how-to/live-camera-demo.ja.md)，現在の実装範囲には[進捗](../status.ja.md)を使う．

「通路に沿って進み，左側のドアへ向かう」と指示する場面を考える．カメラから得られるのは写真であり，写真にモーター指令や座標の一覧が入っているわけではない．写真から役立つ情報を取り出し，指示と結び付け，近くをどう通るか決め，その経路を移動要求へ変える計算が必要になる．この章はモデル内部を説明し，[制御の章](control-loop.ja.md)で通信と実際の動作までつなぐ．

初めて読む場合は上から順に読む．以下の観測・数値は計算を説明するために作った例であり，実際のモデルの返答や，B2で検証済みの動作設定ではない．

## 1．モデルをインストールすると，何が入るのか

**モデル**とは，調整可能な数値を持つ計算の仕組みである．その数値を**パラメータ**または**重み**と呼び，学習で調整する．実行時には重みと入力の数値配列を使い，別の数値配列を計算する．保存した動画を検索して，次に実行する指令を探しているわけではない．

単純な層なら$z=Wx+b$と書ける．入力ベクトル$x$へ学習済み行列$W$を掛け，学習済みベクトル$b$を足す計算である．実際のモデルでは，このような計算，非線形な変換，入力の各部分の関係を扱う計算を繰り返す．重みには学習した振る舞いが反映され，Pythonコードはその重みをどう使うか定める．重みだけでも，Pythonだけでも，全体は動かない．

| 部品 | 担当すること | それだけでは用意されないもの |
|---|---|---|
| 本家TIC-VLAのPython | モデル構造，画像・文章の準備，予測関数 | B2の配線，実機で検証済みの移動制御 |
| InternVL3-1Bの基本資材 | 学習済みの画像・言語部品，設定，語彙 | それだけで完成したナビゲーションへの適応 |
| TIC-VLAのチェックポイント | その構造へ読み込む，学習したナビゲーションの重み | カメラドライバー，時刻，ロボットの認証 |
| このレポジトリの接続コード | 確認済みのローカル読込，入出力検査，記録，表示 | 完成したB2自律走行システム |
| カメラ・ロボットの接続機能 | 実際の観測と，別の機能である移動要求 | 学習した言語指示の理解 |

**チェックポイント**は学習した状態を保存したファイルである．**推論**はその状態を新しい入力へ適用する計算で，通常は重みを変更しない．最初に一回重みを読み込む時間と，その後繰り返す推論の時間は別である．学習は誤差を計算して重みを変える別のプログラムであり，[学習の章](ticvla-training.ja.md)で説明する．

[資材の参照資料](../reference/model-artifacts.ja.md)に使用するファイルを定めている．本家コードや重みを公開レポジトリの外へ置いても，TIC-VLAと無関係になるわけではない．このレポジトリの接続コードが，実行時に別途準備した本家コードを読み込み，別途準備した重みを適用する．

## 2．この論文が解こうとしている問題

**視覚と言語によるナビゲーション**は，周囲を見ながら言語指示に従って移動する課題である．**VLM，vision-language model**は画像と文章を一緒に扱うモデル，**VLA，vision-language-action model**はさらに行動を作る学習部品を持つモデルを指す．ここでの行動はナビゲーションの出力であり，全関節へ直接指令を送ることを意味しない．

言語を含む推論には数秒かかることがある．その間にもロボットや歩行者は動く．写真の解釈が正しくても，使用する時点では古くなっている．別のスレッドで推論すればプログラムの待ち時間を一つ除けるが，それだけでは行動側のモデルに「この情報は過去の場面についてのものだ」と伝わらない．

TIC-VLAは，最新の画像と機体の動き，VLMが作った古い数値表現，その情報の古さと途中の移動量を行動側へ与える．学習時にも遅れた情報を使う．実行方法と学習方法を対応させる点が，理解すべき中心である．[論文3.2〜3.3節](https://arxiv.org/html/2602.02459v2#S3)がこの仕組みを述べている．

例えば，意味情報には「使うドアは左側」と含まれていても，3秒後にはロボットがドアの横を通り過ぎているかもしれない．新しい画像，経過時間，実際の変位が，古い情報を解釈する手掛かりになる．ただし，全ての見えていない変化を正しく扱える保証はなく，届かなかった現在画像を復元する機能でもない．

## 3．一回の予測には何を入力するのか

遅いVLMへ渡す観測を**意味情報の基準観測**，速い行動側へ渡す観測を**現在の行動用観測**として区別する．同じカメラと画像処理モデルを使っても，二つの観測の時刻は異なり得る．

| 入力 | 意味 | 表現 |
|---|---|---|
| 指示 | どの経路・目的地へ進むか | 文章 |
| 意味情報用の画像 | 推論の基準時点の場面と，利用可能ならそれ以前の文脈 | 時刻順のRGB画像 |
| 現在画像 | 今回の行動更新で見えている場面 | RGB画像一枚 |
| 現在の運動 | 現在どう動いているか | 前進・横移動の速度と旋回速度 |
| 基準観測からの運動 | 推論が遅れている間の移動 | 相対変位．具体的な項目は実装で異なる |
| 意味情報の古さ | 基準観測からどれだけ時間が経ったか | 秒 |

**RGB**は各画素の赤・緑・青の強さである．1920×1080の画像なら，前処理前に1920×1080×3個の値を持つ．「ドア」という項目があるわけではない．深度画像は各画素までの推定距離を，LiDARは距離の測定や点群を扱う．現在の接続コードはRGBを使い，ZEDの深度やLivoxの点群はモデルへ入力していない．RGB-Dカメラを接続しても，自動的に深度がモデル入力へ加わるわけではない．

意味情報の基準を50秒，画像を41・44・47・50秒の4枚とする例を考える．意味情報の計算が53秒に終われば，その中の最新画像も既に3秒前である．53秒の行動計算には，行動側の最新画像を別に使う．履歴は時間的な文脈を与えるもので，行動のたびに9秒間待つという意味ではない．

簡単なデモは保存画像一枚を両方へ使い，機体の運動をゼロと明示的に仮定する．同じ画像間の時間差はゼロでも，実際の計算時間はゼロではない．静止した観測の出力を調べる実験には使えるが，動いているロボットで「遅延のない最新観測」と解釈してはいけない．

## 4．画素から画像の特徴へ

**エンコーダー**は入力を別の数値表現へ変える計算部品である．**特徴ベクトル**は，後の計算に役立つよう学習された数値の並びである．**トークン**はそのような表現の系列の一要素を指し，英単語とは限らない．

画像の経路では次を行う．

1. 画像ファイルのバイト列をRGB画素へ復号する．
2. 学習済みエンコーダーが期待する配置へ，画像をリサイズ・前処理する．確認した予測処理は448画素の入力サイズを使うが，カメラも448画素で撮影するという意味ではない．
3. 画素の強さを，学習で使った規約に従う数値へ正規化する．
4. 学習済みの画像モデルを適用して，画像トークンを得る．
5. 対象の観測に応じて，言語側または行動側へトークンを渡す．

実装は固定した[画像処理コード](https://github.com/ucla-mobility/TIC-VLA/blob/9fa6f8b66b9e121d5df5df071297bba8e5353ebb/ticvla/utils/vision.py)と[VLM読込部](https://github.com/ucla-mobility/TIC-VLA/blob/9fa6f8b66b9e121d5df5df071297bba8e5353ebb/ticvla/models/vlm.py)にある．リサイズと正規化は数値の準備であり，それ自体が障害物の検出や地面の距離測定ではない．

**テンソル**は多次元の数値配列である．例えば`[1, L, H]`なら，一件の入力，L個の画像トークン，各トークンH個の数値という配置を表せる．配列の形は分かっても，人を正しく認識したかまでは分からない．行動側は画像の特徴を共通の512次元の表現へ変換してから，他の入力と組み合わせる．

同じエンコーダーの重みで，異なる二枚の画像を処理できる．重みを共有しても，二枚の撮影が同時になるわけでも，一回分の特徴抽出が無料になるわけでもない．実際の計算へGPU時間を割り当てる必要がある．

## 5．画像と指示からVLMの返答へ

**トークナイザー**は固定した語彙表に従い，文章をトークンの識別番号へ変える．トークンには単語の一部，句読点，特別な記号などがある．番号ごとに学習したベクトルを選ぶ．画像用の記号は系列のどこへ画像の表現を入れるか指定するもので，JPEGをモーター制御へ送るものではない．

言語モデルは，指示，画像，それまでの返答のトークン表現を組み合わせる．次に続くトークンの確率を計算し，生成規則に従って一つ選び，追加して繰り返す．これを**自己回帰生成**という．長い説明を出すには，GPU上でも順番に進める計算が何回も必要になる．

固定版の[`TICVLA.predict`](https://github.com/ucla-mobility/TIC-VLA/blob/9fa6f8b66b9e121d5df5df071297bba8e5353ebb/ticvla/models/ticvla.py#L509-L681)は，ナビゲーション用の入力文章を作り，返答を生成し，画像と返答を含む会話全体をもう一度VLMへ通して，行動側が使う数値状態を得る．後半は，完成した会話の表現を取り出す処理であり，別のナビゲーション回答をもう一回作る処理ではない．

入力文章では，移動判断に関係する根拠と，3・6・9秒後の目標を求める．文章中の目標は$(x,y,\theta)$，つまり二つの変位と向きの角度である．返答にはドア，他者の動きらしきもの，課題の進み具合が書かれることがある．これはモデルが生成した文章であり，検証済みの物体検出結果や，内部計算の完全な記録ではない．

**Chain of thought，CoT**は，この学習・入力形式に含まれる説明文を指す名称である．画面の「Generated VLM response」欄には，実際に返ってきた文章をそのまま表示する．モデルの発言と写真を照合する手掛かりにはなるが，もっともらしい説明であることから，メートル単位の経路が正しいとは判断できない．

固定版の予測関数は文章生成にサンプリングを使う．そのため，同じ画像を繰り返し入力しても結果が異なる場合がある．再現性のためには実際の入力と返答を保存する．後から分かりやすい説明へ書き換えると，何が出力されたか隠れてしまう．

## 6．VLMから行動側へは何を渡すのか

主な接続は数値表現であり，文章から「left」を探す処理ではない．その理解のため，まず**アテンション**を説明する．

アテンションでは，取り出したい情報を表す**query**，文脈中の各位置と比較するための**key**，その位置の情報を運ぶ**value**を計算する．代表的な式は次である．

$$
\operatorname{Attention}(Q,K,V)=\operatorname{softmax}\!\left(\frac{QK^\mathsf{T}}{\sqrt d}\right)V.
$$

$Q$・$K$・$V$はベクトルを並べた行列，$d$はkeyベクトルの次元である．$QK^\mathsf{T}$で比較の点数を求め，softmaxで各queryについて合計1となる非負の重みへ変える．それを$V$へ掛け，文脈の情報を重み付きで組み合わせる．学習した数値計算であり，人が読める理由の一覧が出るわけではない．

**Transformer**は，このアテンションと他の学習した変換を使う系列処理の構造である．**KV cache**は各層のkey・value配列を保存する仕組みで，文章生成中の計算の一部を再利用できる．TIC-VLAは，完成したVLMの状態を別のネットワークの入力としても使う．

確認した`ActionExpert._process_kv_cache`は，**最終層のvalue配列**を取り出す．`[batch, heads, sequence, head_dimension]`を`[batch, sequence, heads × head_dimension]`へ並べ直し，各ベクトルを512次元へ変換する．このコードは最後の積が128であることを期待する．したがって「KV cacheを使う」は，全層の全key・valueを行動側が使う意味ではない．[`ActionExpert`の該当箇所](https://github.com/ucla-mobility/TIC-VLA/blob/9fa6f8b66b9e121d5df5df071297bba8e5353ebb/ticvla/models/ticvla.py#L90-L149)で確認できる．

返答も数値表現も，元の会話に依存する．数値表現を画面の文章に置き換えるなら，行動側の接続仕様そのものが変わり，別のコードと検証が必要になる．

## 7．行動側はどうやって30組の座標を出すのか

**Action expert**は，近い将来のナビゲーションを担当する，小さな学習済みネットワークである．**予測ホライズン**は一回の出力が表す将来の時間幅を指す．現在の観測から新しく計算するので，意味情報を再利用しても，古い経路をそのまま再生しているわけではない．

確認した実装は次を行う．

1. 現在画像の特徴を取り出し，512次元へ変換する．
2. 遅れたVLMのvalue特徴も同じ次元へ変換する．
3. 運動・遅延の各数値をベクトルへ変換し，どの入力項目か区別する学習済みの位置表現を足す．
4. これらを並べ，文脈の系列を作る．
5. 将来の出力枠に対応する，学習済みの**action query**を30個用意する．
6. クロスアテンションの層を適用し，各queryが文脈を取り出して組み合わせる．
7. **MLP，多層パーセプトロン**という，学習した変換と非線形関数を重ねた計算で，各queryを二つの数値へ変換する．

Queryは学習するパラメータであって，測定済みの未来画像ではない．この計算の中に「実機を30歩動かす」ループはない．出力の形`[1, 30, 2]`は，一件の入力，30個の予測位置，各位置二つの座標を意味する．

| 状態の項目 | 意味 | 単位 |
|---|---|---|
| `vx` | 現在の前進速度 | m/s |
| `vy` | 現在の左方向への速度 | m/s |
| `yaw_rate` | 現在の向きの変化速度 | rad/s |
| `dx`，`dy` | 意味情報の基準からの変位．その基準の座標系で表す | m |
| `delay` | 現在の行動用観測と意味情報の基準との時間差 | s |

モデルは，これらの項目の意味を学習している必要がある．順番を変えたり，変位の代わりに地図上の絶対位置を入れたり，ラジアンの代わりに度を入れたりすると，数値的に別の問題になる．このレポジトリ側の境界は[状態入力の仕様](../reference/asynchronous-runtime.ja.md)にまとめている．

## 8．経路の座標は厳密には何を意味するのか

**座標系**は原点と軸の向きを定める．確認したデータ処理は，将来位置を現在の機体基準で表し，xを前，yを左とする．公開パッケージの出力はメートルとして解釈する．$(1.0,0.2)$は，基準姿勢から前へ1 m，左へ0.2 mの候補位置であり，速度でも画素座標でもない．

全ての点が同じ原点を使う．$(0.1,0)$・$(0.2,0)$・$(0.3,0)$なら，終点は前方0.3 mである．これらを足すと，誤って0.6 mになる．パッケージは位置を直接返し，接続コードは累積和を取らない．[データ生成部](https://github.com/ucla-mobility/TIC-VLA/blob/9fa6f8b66b9e121d5df5df071297bba8e5353ebb/data/s01_batch_json_generation.py)と[行動用データセット](https://github.com/ucla-mobility/TIC-VLA/blob/9fa6f8b66b9e121d5df5df071297bba8e5353ebb/ticvla/data/policy_data.py)がこの規約の根拠になる．

コードは30枠を0.1秒間隔に対応させ，このレポジトリの接続コードは0.1〜3.0秒のラベルを付ける．予測した時刻であり，B2が実際に到着した時刻ではない．経路の形だけを追う制御器なら，その時刻に到着するとは限らない．時刻付き軌跡を追うには，速度と時間も明示的に制御する必要がある．

画面には，異なる意味を持つ二つの長さがある．

$$
d_{\mathrm{end}}=\sqrt{x_{30}^{2}+y_{30}^{2}},\qquad
L=\sum_{i=1}^{30}\|p_i-p_{i-1}\|,\quad p_0=(0,0).
$$

$d_{\mathrm{end}}$は終点までの直線距離，$L$は表示した折れ線の長さである．どちらも実際に歩いた距離の測定ではない．画面は自動で拡大・縮小するため，見た目の線の長さではなくメートルの軸を読む．

深度がないのにメートルを出せるのは，学習で見た目や運動とメートル単位の軌跡を対応させるからである．統計的な関係を学ぶのであって，厳密な距離計になるわけではない．カメラの高さ，画角，切抜き，取付角度，ロボットの形が変われば，その関係が崩れる可能性がある．B2で必要な確認は[制御の章](control-loop.ja.md)で詳しく扱う．

## 9．論文と公開パッケージは区別して読む

論文，実験，公開コード，チェックポイントは関係する資料だが，同じ仕様そのものではない．ここで確認したsource版は`9fa6f8b66b9e121d5df5df071297bba8e5353ebb`である．接続コードは，対応しない層を未学習のまま残さず，重みの項目と形を厳密に検査する．

| 項目 | 論文の記述 | 確認したパッケージ・チェックポイントの経路 |
|---|---|---|
| 行動の出力 | 三成分の移動増分を累積して軌跡にする | XY位置を直接出力．累積和なし |
| 行動側のアテンション層 | 付録Aでは6層 | 読み込んだ重みでは3層 |
| 運動の追加情報 | 向きの変化量も含む | 運動5数値と遅延．独立した向き変化量の枠はない |
| 意味特徴の次元変換 | 付録には別の入力幅が記載される | コードは最終層valueの幅128を期待 |
| 簡単な予測関数の実行 | 論文は非同期の実行を説明 | パッケージの`predict()`は完了まで待つ |

論文側は[付録A](https://arxiv.org/html/2602.02459v2#A1)，パッケージ側は[モデルのコード](https://github.com/ucla-mobility/TIC-VLA/blob/9fa6f8b66b9e121d5df5df071297bba8e5353ebb/ticvla/models/ticvla.py)と[厳密な読込部](../../src/b2_tic_vla/inference.py)が根拠である．図をそのまま接続仕様に使えない理由になるが，公開版がいつ，なぜ変わったかを確定するものではない．学習の全段階を再現したわけでも，取得した重みの厳密な学習履歴を確定したわけでもない．

図へ合わせるためだけに三列目を足したり，層を3個増やしたり，XYを累積したりしない．いずれもチェックポイントの意味を変えてしまう．

## 10．遅い処理と速い処理はどうやって同時に進むのか

**同期実行**は，ある計算が終わってから，それに続く計算へ進む方式である．**非同期実行**は，その計算が未完了でも別の役立つ処理を進められる方式である．**並行実行**は，時間の重なる期間に複数の仕事が進むことを指し，GPUの計算が厳密に同じ瞬間に実行される保証ではない．

同期のカメラ予測は，おおむね次の順になる．

```text
Read image A -> generate text -> extract conversation features
             -> decode path for A -> save/display -> next prediction
```

文章を作っている間，この予測処理から新しい経路は出ない．別のプレビューで写真だけ更新しても，予測経路が同じ頻度で新しくなるわけではない．

非同期方式では，完成した**意味情報の組**を保持する．内容は，特徴，返答，基準画像の時刻，基準姿勢，結果を区別する識別子である．一つの仕事が次の組を計算し，別の仕事が最後に完成した組と新しい画像・運動状態を繰り返し組み合わせる．完成後に組全体を切り替えるため，ある画像の特徴へ別の画像の時刻が付く取り違えを防ぐ．

以下は，古い完成済みの組が既にあり，新しい意味情報を10.0秒の観測から作り始め，13.0秒に完成する例である．

| 時刻 | 意味情報の仕事 | 行動の仕事 |
|---|---|---|
| 10.0秒 | 10.0秒を基準に計算開始 | 古い完成済みの組と，10.0秒の画像・状態を使う |
| 10.2秒 | まだ計算中 | 同じ古い組と，10.2秒の画像・状態で計算し直す |
| 12.8秒 | まだ計算中 | 計算し直す．古い組の経過時間はさらに増える |
| 13.0秒 | 基準10.0秒の組を公開 | 完成した組へ切替可能．その古さは既に3.0秒 |
| 13.2秒 | 次の組を計算してよい | 13.2秒の画像・状態，基準10.0秒，古さ3.2秒を使う |

意味情報の基準時刻を$t_r$，完成を$t_c$，行動用観測を$t$とすると，

$$
\Delta t=t-t_r=(t_c-t_r)+(t-t_c).
$$

第一項は結果が使えるまでの時間，第二項は完成後に再利用した時間である．基準を完成時刻へ置き換えると，第一項が消えてしまう．その間に0.4 m移動したなら，変位も同じ組の基準座標で表す．

起動直後は完成した組がない．後には古くなりすぎたり，計算に失敗したりする．制御するプログラムには，各場合の動作を明示する必要がある．非同期だからといって，最後の情報を永遠に使えるとは限らない．

二つの仕事はJetsonの計算資源を共有する．スレッド，プロセス，CUDA streamは仕事の割当ての仕組みであり，期限の保証ではない．画像特徴の抽出，行動の計算，状態との対応付け，配送まで含めて測定する．タイムアウトを長くしても計算そのものは速くならない．

**プロセス**は，自分のアドレス空間を持つ実行中のプログラムである．**スレッド**は一つのプロセス内の実行の流れで，同じ読込済みモデルを共有できる．**CUDA stream**はGPUの演算を順番に並べる待ち行列である．別のstreamなら実行時に独立した列として割り当てられるが，計算資源や依存関係によって待つ場合もある．したがって，二つのスレッドはGPU二台という意味ではなく，二つのコンテナも自動的に別々のモデルやGPUを持つ意味ではない．

依存関係に注目すると，仕事の割当ては次の擬似コードで説明できる．誤り・期限切れの扱いを省いて構造を示したもので，実行するロボットプログラムではない．

```text
repeat while observation experiment is running:
    if semantic job finished:
        publish its complete result with its original reference
    obtain the newest image and associated measured motion
    if no semantic job is running:
        start a new semantic job; do not wait for completion here
    if a valid completed semantic snapshot exists:
        calculate age and displacement from that snapshot's reference
        calculate a new action path using the current image
        record the path
    else:
        record that no usable semantic context exists
```

「待たない」は，新しく起動した意味情報の仕事についてである．行動計算自体には時間がかかり，その経路を記録するには必要な結果を待つ．その間にも意味情報のスレッドは進められる．次の一巡では新しい画像を取り，たまった古い画像を必ず全て処理するわけではない．意味情報が完成すれば，次の行動計算で使えるようになり，途中まで書き込んだテンソルを公開しない．

現在の観測実験では，カメラの取得側とモデルの観測側を別コンテナにし，専用SSDフォルダで完成画像と付随情報を渡す．モデル側からは読取り専用である．モデルのプロセス内では，workerスレッドとmainスレッドが読込済み重みを共有し，別のCUDA streamを使う．つまり，カメラを独立に取得する並行処理と，意味情報・行動の仕事を重ねる並行処理の二段階がある．コンテナの境界は[配置の解説](deployment-design.ja.md)でさらに説明する．

## 11．現在のレポジトリでは何が動くのか

モデルの実行経路は二つあり，どちらも現在はB2を動かさない．

**同期デモ**．[`TicVlaPredictor`](../../src/b2_tic_vla/inference.py)が確認済みのローカル資材を読み，予測関数を呼び，有限値の`[1, 30, 2]`を検査して`Plan`を作る．[`camera_demo.py`](../../tools/camera_demo.py)が撮影，予測，HTML表示を組み合わせる．青い線は行動のテンソルから作り，返答から座標を解析して描くのではない．

**非同期の観測実験**．[`observe_async.py`](../../tools/observe_async.py)と[`semantic_cache.py`](../../src/b2_tic_vla/semantic_cache.py)が意味情報の仕事と現在観測による行動計算を扱う．現状の意味情報側は同期関数を使い，使わない行動計算も一回含むため，論文の最適化済み実行を再現したものではない．静止運動を仮定し，モーター要求は送らない．[実験記録](../records/async-shadow.ja.md)には，完成した行動だけでなく，起動・更新時の大きな空白も残している．

別のB2用ツールで機体の状態を受信できても，自動的にモデル入力へつながるわけではない．単位，座標系，時刻を確立し，仮定の運動を対応する測定へ置き換え，有用な行動更新を継続し，別途検証する指令経路を実装する作業が残る．

次は[重みが学習される仕組み](ticvla-training.ja.md)，続いて[経路からB2への移動要求](control-loop.ja.md)を読む．起動コマンドは操作手順に置き，この章ではそのコマンドが起こす計算を説明する．
