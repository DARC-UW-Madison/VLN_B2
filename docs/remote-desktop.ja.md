# Macからのリモートデスクトップ

[English](remote-desktop.md) · [システム全体像](system-overview.ja.md) · [現地手順](field-network.ja.md)

Macからネットワーク越しにJetsonの画面を操作できる．2026-10-27の読み取り調査では，
Vino 3.22は導入済みだが，`vino-server`のプロセスとTCP 5900・3389の待受はなかった．
XRDP・xorgxrdp・gnome-remote-desktopは未導入で，遠隔画面のサービスや認証設定を有効にしていない．

転送を使う前に，[Tailscaleの公式セキュリティ告知](https://tailscale.com/security-bulletins)を確認する．
調査した導入版は1.104.2で，2026-10-26のSSHの告知TS-2026-014・015の修正版は1.104.4以上である．
動作中の版とポリシーを確認し，現地・別経路での復旧を確保してから，適切に更新して
Tailscale SSHのトンネルを試す．唯一の遠隔経路を，復旧手段なしに再起動しない．ここで更新・SSH方針の変更はしていない．

## 何を通信するか

VNCは画面の更新とキーボード・マウス操作を送り，計算はJetsonで行う．SSHは端末の操作を送る．
どちらもネットワークが必要である．確認後は通常のHDMI利用を省けるが，Wi-Fiの切断を
そのWi-Fi経由の遠隔画面で復旧することはできない．

既存のVinoはログイン済みのGNOME画面を共有するもので，ログイン画面へ接続する方式ではない．
[NVIDIAのVNC手順](https://developer.nvidia.com/embedded/learn/tutorials/vnc-setup)にもこの条件がある．
Wi-Fi・SSHがGUIログイン前から動いても，ユーザーセッションのVNCが利用可能になるわけではない．
それも必要なら，別のログイン・セッション方式の選定とJetsonでの検証が必要で，未導入である．
Ubuntu 20.04に，新しいUbuntuと同じRDP設定画面があるとは仮定しない．

## 有効化前の接続案

認証付きSSHトンネルから，localhostへ制限したVNCサーバーへ接続する構成を優先する．
有効化前に待受・認証とMacクライアントの互換性を調べる．以下は，サーバーを設定し，
Jetsonのループバック5900番で待ち受けることを確認した後だけ使う例である．

```sh
ssh -N -L 127.0.0.1:5901:127.0.0.1:5900 RESEARCH_USER@JETSON_MANAGEMENT_ADDRESS
```

トンネルを作った後，Macの別の端末で開く．

```sh
open vnc://127.0.0.1:5901
```

最初のアドレスはMacの待受，後のループバックはSSHがJetson側で接続する宛先である．
`-N`は遠隔のシェルを開かず，`-L`はローカルTCPポートを転送する．画面共有中はトンネルを維持する．
大学LANへVNCのポートを公開せずに使える．VNCパスワードをコマンドへ書かず，認証を無効化せず，
保護された通信方式を確認せずに古い暗号化設定をコピーしない．現在サーバーは待ち受けておらず，接続例も未実行である．

## 現地での合格条件

1. どのデスクトップ・セッションを共有し，そのユーザーがどうログインするか確認する．
2. 認証を手元で設定し，待受・通信へのアクセスを制限できていることを検証する．
3. Macの画面，キーボード・マウス，解像度，ロック・ログアウト時，GPUとの相性を確認する．
   共有する録画へ個人の認証画面を入れない．
4. 再起動後とHDMIを外した状態を試す．GUIが有効なだけでは使える画面の生成を証明できず，
   対応する表示・仮想セッション設定が必要な場合がある．遠隔操作中にグラフィックス設定を無作為に変えない．
5. 最初の起動・通信試験は現地の復旧手段を残す．その後，大学Wi-Fiなしの承認された移動用LANでも同じ接続を試す．

リモートデスクトップは管理用である．将来のローカル推論・制御ループは，Macの画面やSSH端末とは
独立した起動・終了と停止方針を持つ必要がある．
